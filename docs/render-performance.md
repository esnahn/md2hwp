## 문단 스타일 선택 내보내기

`ApplyResolvedParagraphStyle`의 전체 문서 읽기를 마지막 본문 문단의 선택 블록 읽기로
바꿨습니다. [한컴 공식 답변](https://forum.developer.hancom.com/t/topic/2966)처럼 현재
스타일을 직접 가져오는 API가 없어, 실제 문단을 `GetTextFile("HWPML2X", "saveblock")`으로
읽습니다. 반환된 문단의 로컬 Style ID를 그 XML의 STYLE.Name으로 해석합니다. 블록 저장은
ID를 재번호화하므로 원래 문서의 ID와 비교하지 않으며, 스타일 적용에는 원래 ID를 사용합니다.
같은 스타일이면 다른 선언 스타일을 거쳐 다시 적용하는 기존 대화상자 회피 방식은 유지합니다.

한글 2020 시험에서는 앞 문단과 빈 마지막 문단을 함께 선택해도, 끝의 빈 문단이 실제
`본문` 대신 `바탕글` 스타일로 내보내졌습니다. 역방향 선택과 전체 선택도 같았습니다.
따라서 임시 작업 문서의 끝에 제로폭 공백 `U+200B` 한 글자를 넣고, 그 글자만 선택해 내보낸 뒤 즉시
지웁니다. 앞 문단의 표·그림과 긴 본문은 선택하지 않습니다. 한글이 선택 블록에 함께 넣는
SECDEF/COLDEF와 머리말 문단은 스타일 판단에서 제외합니다.

삽입 전후 좌표, 선택 종류, 내보낸 문자, 삭제 직전의 좌표·선택 해제와 삭제 후 커서 위치를
확인합니다. 삽입·내보내기·해석·삭제 중 오류가 나면 변환을 중단하고 이전 결과를 보존합니다.
변경 내용 기록이 켜져 있으면 임시 문자를 넣지 않고 기존의 전체 문서 읽기로 되돌아갑니다.
편집 이력과 수정 상태는 임시 문서에서 바뀔 수 있으므로 문서 무변경 조회라고 보지 않습니다.
입력 원고와 템플릿 파일은 변경하지 않습니다.

빈 문단, 굵게·기울임이 적용된 빈 문단, 문단 나눔 직후, 새 빈 문서에서 임시 문자 입력 전과 삭제 후의
전체 HWPML이 정확히 같았고, 커서 및 입력 글꼴·크기·굵게·기울임·자간·장평·색상·밑줄도
복원됐습니다. 순수 계약 테스트는 선택 블록 ID 재번호, 구역 설정, 변경 내용 기록의 fallback,
실패 정리와 원래 문자 삭제 방지를 확인합니다. 실제 모든 기능 원고 변환도 저장·재열기
검증을 통과했습니다.

제로폭 공백은 최초 구현의 ASCII `x`를 대체했습니다. 한글 2020에서 기본 문단과 `본문`
스타일의 빈 문단·굵게/기울임 문단·내용이 있는 문단·문단 나눔 직후를 시험했습니다.
선택 XML에 `U+200B` 한 글자가 보존됐으며, 실제 이름 있는 문단 스타일도 유지됐습니다.
임시 문자 입력 전과 삭제 후의 전체 HWPML·커서·입력 서식은 일치했습니다.
전체 기능 샘플에서도 선택 스타일 조회 99회를 수행하고 저장·재열기 검증을 통과했습니다.

아래 대규모 성능 측정과 112쪽 이미지 비교는 ASCII `x`를 사용한 빌드의 기록입니다.
제로폭 문자 교체 후 대규모 시간 계측과 시각 검사는 반복하지 않았습니다.
교체 검증 로그·XML·샘플 결과는 ignored `artifacts/paragraph-style-profile/zero-width/`에 보관합니다.

## 남은 단축 방안과 우선순위

현재 병목은 원고 파싱이나 마지막 저장보다 **자라나는 문서 전체를 반복해서 읽는 작업**입니다.
한컴의 [공식 Automation 문서](https://github.com/hancom-io/devcenter-archive/blob/main/hwp-automation/HwpAutomation.pdf)
역시 `GetTextFile`이 내부 저장과 여러 메모리 복사를 수행하므로 느릴 수 있다고 설명합니다.

1. **문서가 변하지 않는 검증 구간에서 실제 XML snapshot을 공유합니다.**
   삽입 후 하이퍼링크 제거 뒤의 일곱 번 읽기, 첫 저장·재열기 뒤의 열 번 읽기를 각각
   하나로 줄일 수 있습니다. 모든 기존 검증에는 동일한 실제 문서와 파생 문단 목록을
   제공하고, 삭제·import·재열기 뒤에는 반드시 새로 읽습니다. 검증 항목을 줄이는 방안이 아닙니다.
2. **그림·박스 복제 직후 읽은 문서를 다음 내용 교체 전 검사에 재사용합니다.**
   이 원고에서는 그림 29회·박스 14회의 중복 읽기가 후보입니다. 복제 이후 새 문서를
   읽는 검사는 유지하며, 실제 COM 변경 사이의 문서를 공유하지 않습니다.
3. **전체 문자열 export 대신 임시 파일로 저장 후 읽는 방식도 비교할 수 있습니다.**

   공식 문서의 권장 후보지만, 디스크 접근·파일 수명·실패 복구 비용을 포함한 별도
   측정이 필요합니다. API 이름만 바꾸어 더 빨라진다고 가정하지 않습니다.

위 방안은 아직 적용하지 않았습니다. 앞서 적용한 문단 스타일 조회 최적화 이후에도 그림·박스
복제와 검증의 전체 XML 읽기는 남습니다. 위 호출 수가 줄어드는 만큼 시간이 비례해서
줄어들지는 않으므로, 변경한 단계의 호출 수와 전체 변환 시간을 함께 비교해야 합니다.

## 개발용 계측 방법

`MD2HWP_PROFILE=1`을 설정하면 백엔드가 stderr에 `md2hwp-profile:` 한 줄과 JSON을
출력합니다. 평소에는 출력하지 않으며 렌더링·보안 확인·구조 검증을 바꾸지 않습니다.

```powershell
$env:MD2HWP_PROFILE = '1'
.\target\release\md2hwp.exe .\examples\korean-lorem\large-5x.md --template .\templates\template.hwp --verbose 2> .\profile.log
Remove-Item Env:\MD2HWP_PROFILE
```

`TotalMilliseconds`는 C# 호출 범위, `Metrics`는 호출자별 내보내기·파싱과 단계·개체별
시간입니다. `hwpml.export/`는 전체 문서, `hwpml.block.export/`는 새 스타일 조회의
선택 블록 읽기입니다. 두 집계를 분리하며, 다른 기존 saveblock 호출은 이 별도 집계에
포함하지 않습니다. `Completed: false`인 실행은 실패한 실행이며, 중간 실패 시 완료되지 않은
단계의 시간이 빠질 수 있습니다. 정상 완료 실행끼리 비교하십시오.

원시 실행 로그·JSON·입력 사본·결과 HWP는 ignored `artifacts/render-profile/`에 보관합니다.
이 문서는 수치와 해석을 기록하며 원시 바이너리의 해시 일치를 실행 조건으로 요구하지 않습니다.
