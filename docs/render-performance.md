# 대규모 문서 변환 시간 측정

2026-10-05에 한글 2020 11.0.0.9136과 Release 빌드로 대규모 기능 원고를 측정했습니다.
입력은 강조 문법 수정 전의 `examples/korean-lorem/large-5x.md` 사본이며, 본문 11,155어절,
그림 29개·표 39개·박스 14개·각주 66개·상호참조 36개를 포함합니다.
`templates/template.hwp`를 명시했고, 입력·이미지·템플릿을 동일하게 보존했습니다.
이 측정 빌드는 시간 계측만 추가했으며 표 머리행 보정은 아직 포함하지 않았습니다.

## 실제 측정

Rust 명령 전체는 **634.615초(10분 35초)**, C# 변환 호출은 **633.020초**였습니다.
종료 코드 0, 저장·재열기 검증을 통과했습니다. 페이지 이미지 출력은 포함하지 않습니다.
이전 비계측 실행은 643.364초였으므로 이 차이를 최적화 효과로 보지 않습니다.
단일 워크스테이션에서 각 한 번 측정한 값이며, 실행마다 변동할 수 있습니다.

| 항목 | 호출 | 누적 시간 | C# 전체 시간 대비 |
| --- | ---: | ---: | ---: |
| 전체 HWPML 내보내기 | 855회 | 485.466초 | 76.69% |
| 내보낸 HWPML 파싱 | 855회 | 27.747초 | 4.38% |
| 문단 스타일 확인용 내보내기 | 473회 | 265.431초 | 41.93% |
| 그림 캡션 복제·검증용 내보내기 | 148회 | 84.527초 | 13.35% |
| 그림 출처 복제·검증용 내보내기 | 108회 | 61.591초 | 9.73% |
| 박스 복제·검증용 내보내기 | 99회 | 57.925초 | 9.15% |

아래 단계 시간과 위 호출 시간은 **중첩**됩니다. 두 표를 합산하면 중복 계산합니다.

| 단계 | 시간 |
| --- | ---: |
| 템플릿 준비·원형 바인딩 | 2.281초 |
| 본문·목록·그림·박스·표 자리 삽입 | 538.327초 |

| 최종 구조 검증 | 10.469초 |

COM 생성·해제 등은 C# 전체 시간에 포함되지만 별도 단계로 나누지 않았습니다.
선택 블록의 `saveblock` 읽기는 위 전체 HWPML 내보내기 집계에서 제외하며, 해당 단계
시간에는 포함됩니다. 전체 내보내기를 통해 반환된 문자열은 누적 4,493,742,522개의
UTF-16 코드 유닛입니다. 이는 반복해서 읽은 총량이며, 메모리 최고 사용량이나 HWP 크기가 아닙니다.

## 표 머리행 보정 적용 후 실행

2026-10-06에는 강조 경계 네 곳을 수정한 현재 원고와 표 보정 빌드로 다시 실행했습니다.
Rust 명령 전체는 **779.527초(12분 59.5초)**, C# 호출은 **776.217초**였습니다.
머리행이 고립된 표 7개를 보정하고, 모든 생성 표의 실제 쪽·단 위치를 최종 저장·재열기
뒤에도 확인했습니다. 종료 코드 0이며, 출력은 112쪽입니다. 쪽 이미지 출력 시간은 제외합니다.

| 항목 | 결과 |
| --- | ---: |
| 전체 XML 내보내기 | 870회 / 492.622초 / C# 시간의 63.46% |
| 문단 스타일 확인용 내보내기 | 473회 / 263.281초 |
| 표 시작 배치 검사·보정 | 128.736초 |
| 마지막 재열기 검증(표 위치 재검사 포함) | 27.041초 |

표 보정 단계에는 실제 셀 위치 읽기, 고립된 표의 쪽 나눔 추가, 전체 문서 재import
7회와 구조·상호참조 재검사가 포함됩니다. 128.736초 전체를 import 자체의 시간으로
해석하지 않습니다. 최종 재열기 검증은 별도 단계이며 위 표 보정 시간에 포함되지 않습니다.

첫 기준 실행과는 문법·검증 기능이 달라 직접적인 최적화 비교가 아닙니다. 추가한
배치 보정의 비용도 있으며, 이번 작업은 속도를 개선했다는 결과가 아닙니다.
본문 삽입과 스타일 확인의 전체 XML 읽기가 여전히 가장 큰 단축 후보입니다.
표 보정의 반복 import·참조 검사를 줄이는 후속 설계도 후보지만, 앞 표의 변경에 따라
뒤 표를 다시 측정하는 동작과 원래 필드·서식 검증을 유지해야 합니다.
후속 실행 로그·계측 JSON·결과 XML·쪽 이미지는 ignored `artifacts/table-header-fix/`에 보관합니다.

## 단축 방안과 우선순위

현재 병목은 원고 파싱이나 마지막 저장보다 **자라나는 문서 전체를 반복해서 읽는 작업**입니다.
한컴의 [공식 Automation 문서](https://github.com/hancom-io/devcenter-archive/blob/main/hwp-automation/HwpAutomation.pdf)
역시 `GetTextFile`이 내부 저장과 여러 메모리 복사를 수행하므로 느릴 수 있다고 설명합니다.

1. **문서가 변하지 않는 검증 구간에서 실제 XML snapshot을 공유합니다.**
   삽입 후 하이퍼링크 제거 뒤의 일곱 번 읽기, 첫 저장·재열기 뒤의 열 번 읽기를 각각
   하나로 줄일 수 있습니다. 모든 기존 검증에는 동일한 실제 문서와 파생 문단 목록을
   제공하고, 삭제·import·재열기 뒤에는 반드시 새로 읽습니다. 검증 항목을 줄이는 방안이 아닙니다.
2. **그림·박스 복제 직후 읽은 문서를 다음 내용 교체 전 검사에 재사용합니다.**
   이 원고에서는 그림 29회·박스 14회의 중복 읽기가 후보입니다. 복제 이후 새 문서를
   읽는 검사는 유지하며, 실제 COM 변경 사이의 문서를 공유하지 않습니다.
3. **문단 스타일의 내부 상태 추적을 별도로 설계합니다.**
   473회 읽기를 줄이면 가장 큰 개선 여지가 있지만, 같은 스타일 재적용 시 뜨는
   덮어쓰기 대화상자를 방지해야 합니다. `STYLE.NextStyle` 전이와 네이티브 목록,
   박스·캡션 붙이기, import·재열기 뒤의 상태를 모두 다뤄야 합니다.
   확인 없이 `GetDefault` 값으로 대체하거나 덮어쓰기 확인을 자동 수락하지 않습니다.
   [한컴 공식 답변](https://forum.developer.hancom.com/t/topic/2966)은 현재 스타일을
   직접 가져오는 방법이 없다고 설명합니다.
4. **전체 문자열 export 대신 임시 파일로 저장 후 읽는 방식도 비교할 수 있습니다.**
   공식 문서의 권장 후보지만, 디스크 접근·파일 수명·실패 복구 비용을 포함한 별도
   측정이 필요합니다. API 이름만 바꾸어 더 빨라진다고 가정하지 않습니다.

앞의 두 방안은 영향 범위가 작습니다. 세 번째는 효과 후보가 크지만 스타일·목록
계약과 실제 한글의 대화상자 회피를 함께 검증해야 합니다. 표 글꼴 측정이나 서식 정의
검색의 CPU 캐시도 후보이나, 현재는 전체 XML 내보내기의 비중이 더 큽니다.
위 호출 수가 줄어드는 만큼 시간이 비례해서 줄어들지는 않습니다. 실제 최적화와
후속 비교 측정은 아직 하지 않았습니다.

## 개발용 계측 방법

`MD2HWP_PROFILE=1`을 설정하면 백엔드가 stderr에 `md2hwp-profile:` 한 줄과 JSON을
출력합니다. 평소에는 출력하지 않으며 렌더링·보안 확인·구조 검증을 바꾸지 않습니다.

```powershell
$env:MD2HWP_PROFILE = '1'
.\target\release\md2hwp.exe .\examples\korean-lorem\large-5x.md --template .\templates\template.hwp --verbose 2> .\profile.log
Remove-Item Env:\MD2HWP_PROFILE
```

`TotalMilliseconds`는 C# 호출 범위, `Metrics`는 호출자별 내보내기·파싱과 단계·개체별
시간입니다. `Completed: false`인 실행은 실패한 실행이며, 중간 실패 시 완료되지 않은
단계의 시간이 빠질 수 있습니다. 정상 완료 실행끼리 비교하십시오.

원시 실행 로그·JSON·입력 사본·결과 HWP는 ignored `artifacts/render-profile/`에 보관합니다.
이 문서는 수치와 해석을 기록하며 원시 바이너리의 해시 일치를 실행 조건으로 요구하지 않습니다.
