# rhwp 백엔드 범위와 사용

검토일: 2026-10-19. md2hwp 기준은 v0.4.4 (`54caa0d`), 작업 브랜치는
`codex/rhwp-backend`이다. 최초 소스 검토 뒤 무편집 저장 시험을 수행했다.
실행·한글 재열기·페이지 비교 결과는 [시험 보고서](rhwp-roundtrip-2026-10-19.md)에 있다.
사용자 결정에 따라 rhwp 백엔드는 HWP 템플릿과 HWP 출력만 지원한다.
HWPX 보존 문제는 이번 구현 범위에서 제외하며, 기존 한글 백엔드가 HWPX를 계속 담당한다.

## 현재 배포와 자동 선택

현재 개발 빌드와 실행용 ZIP에는 `md2hwp-rhwp.exe`와 `md2hwp-hancom.exe`를 함께 넣는다. `--worker`를 생략하면 EXE 옆의 rhwp를 우선하고, 파일이 없을 때 한글 백엔드를 선택한다. 템플릿 또는 출력이 `.hwpx`이면 한글 백엔드만 자동 선택한다. 명시한 `--worker`는 그대로 사용하며, 실행·검증 실패 후 다른 백엔드로 재시도하지 않는다. HWPX를 명시한 rhwp에 전달하면 명확히 거부한다. 한글 백엔드와 `hwp2pdf.exe`의 한글·.NET·보안 모듈 의존은 유지한다.

사용자는 현재 남은 템플릿·레이아웃 제한을 수용해 기본 선택 변경을 승인했다. 한글의 JPEG 재인코딩에 따른 관찰된 표시 차이는 허용한다. 이 결정은 임의 템플릿의 완전한 동등성이나 긴 박스·표의 잘림 안전성을 입증하지 않는다. [기능 동등성 검토](rhwp-parity-2026-10-23.md)와 아래 날짜별 증거의 범위를 유지한다.

## 초기 검토 결론

rhwp를 Rust 라이브러리로 연결하는 HWP 전용 백엔드를 만든다.
무편집 저장 시험 결과를 바탕으로 HWP 최소 생성 시험을 진행한다.
C# 백엔드는 비교 기준이자 HWPX 지원 경로로 유지한다.
IR 0.4와 원고 문법, 템플릿 태그는 엔진 교체만을 이유로 변경하지 않는다.

## 확인한 upstream

공식 GitHub API에서 확인한 최신 릴리스는 v0.8.7(2026-10-06), main은
`1a76570e833917d15817415a53c09ad61ab3203f`이다. 다음 근거는 이 커밋에 고정한다.

- [Cargo.toml](https://github.com/edwardkim/rhwp/blob/1a76570e833917d15817415a53c09ad61ab3203f/Cargo.toml): rlib/cdylib 제공. 브라우저/WASM을 거치지 않는 Rust 연결 후보이다.
- [공개 라이브러리](https://github.com/edwardkim/rhwp/blob/1a76570e833917d15817415a53c09ad61ab3203f/src/lib.rs): DocumentCore, parser, model, serializer 노출.
- [저장 API](https://github.com/edwardkim/rhwp/blob/1a76570e833917d15817415a53c09ad61ab3203f/src/serializer/mod.rs): HWP/HWPX serializer 및 content-loss report 제공. API 존재만으로 우리 개체의 보존을 보장하지 않는다.
- [지원 범위](https://github.com/edwardkim/rhwp/blob/1a76570e833917d15817415a53c09ad61ab3203f/README.md): HML은 제한 지원이며 그림·리소스 등 미지원 요소의 손실 저장을 차단한다. 따라서 기존 HWPML 합성 결과를 그대로 입력하는 경로는 우선안에서 제외한다.
- [MIT 라이선스](https://github.com/edwardkim/rhwp/blob/1a76570e833917d15817415a53c09ad61ab3203f/LICENSE): 저작권·허가문 보존 필요. 실제 도입 시 선택 feature의 전이 의존성과 자산까지 별도로 점검하고 배포 고지를 갱신한다.

## 현재 코드에서 가져갈 것

Release는 이미 `DirectXmlFlatDocument.cs`에서 IR과 템플릿으로 HWPML을
합성한다. COM은 주로 템플릿 해석, 그림 리소스와 개체 identity 생성,
native 상호참조, 일부 목록 측정, 표 페이지 보정, 저장·재열기에 남아 있다.

| 현재 역할 | 이전 방안과 주의점 |
| --- | --- |
| Rust Pandoc→IR 검증 | 그대로 유지. rhwp의 Document 모델과 공개 IR을 분리한다. |
| 템플릿 선언·범위·서식 복제 | rhwp 어댑터에 포팅. 정적 문서 영역과 미사용 서식을 함께 보존한다. |
| 제목 카운터·고정 제목 참조 | 기존 의미와 테스트를 재사용한다. 템플릿 의존 코드 제목 처리를 IR로 옮기지 않는다. |
| 그림·캡션·각주 | native 개체와 리소스 ID 할당을 구현한다. 그림·표 번호와 참조를 일반 텍스트로 축소하지 않는다. |
| 표 폭·페이지 분할 | `TableAutoWidths.cs`의 Windows GDI 측정과 `NativeTablePagination.cs`의 실제 페이지 보정은 별도 대체 과제다. |
| 최종 검증 | HWPML 문자열 일치에 종속되지 않는 구조 비교가 필요하다. 한글에서 다시 열어 보는 독립 검증을 개발 단계에 유지한다. |
| hwp2pdf | 별도 과제. md2hwp 생성 백엔드 교체가 PDF 출력 동등성을 의미하지 않는다. |

## 제안 구조

`Markdown/Pandoc JSON → md2hwp IR → 템플릿 바인딩/생성 계획 → rhwp 어댑터 → HWP`

공개 IR에 rhwp 타입을 노출하지 않는다. 어댑터만 upstream 모델/API에 의존하며
revision을 고정한다. 사용자가 동의한 구조는 rhwp 라이브러리를 직접 링크하는
별도 `md2hwp-rhwp.exe`이며, 기존 `--worker`로 선택하고 백엔드 단독 실행도
지원한다. 기존 백엔드와 IR+템플릿→출력 계약 및 CLI를 맞춘다.
rhwp 백엔드에서 .hwpx 템플릿 또는 출력 경로를 받으면 생성 전에 명확한
미지원 오류를 반환한다. 기존 한글 백엔드 선택을 안내하며 자동 전환하지 않는다.
이번 무편집 시험 EXE는 이 제품용 백엔드와 구분한다.
HWP 기능을 옮긴 후 rhwp 실행 경로의 .NET/한글 의존을 제거할 수 있다.
글꼴 측정과 PDF까지 포함한 플랫폼 독립 여부는 따로 판단한다.

## 초기 단계와 통과 조건

1. **무편집 왕복 저장 시험**
   - 기본 템플릿과 전체 기능 출력 문서를 고정 입력으로 사용한다.
   - HWP→HWP를 통과 대상으로 한다. 이미 수행한 HWPX·교차 저장 시험은 조사 기록으로만 남긴다.
   - 텍스트, 실제 서식 정의, 페이지/구역 설정, 머리말·꼬리말·바탕쪽,
     그림 데이터, native 캡션·각주·필드와 참조 관계를 비교한다.
   - rhwp 자체 재열기뿐 아니라 한글 재열기와 같은 한글 렌더러의 페이지 비교를 한다.
   - 실패하면 파서/serializer 보존 문제를 먼저 해결한다. 이 단계 전에 본문 생성기를 포팅하지 않는다.
2. **최소 생성 시험**
   - 본문·제목·메타데이터를 HWP 템플릿 샘플에서 복제하고 HWP로 저장한다.
   - 태그가 여러 글자 run에 걸친 경우, 서식 ID 재매핑, 정적 영역 보존을 검증한다.
3. **기능별 확대**
   - 목록 → 코드 → 그림·캡션/출처 → 표 → 각주 → native 상호참조 순으로 확대한다.
   - once/except.once, each.child, 제어문자, 개체 앞뒤 빈 문단도 기존 계약 그대로 확인한다.
   - PNG/JPEG/EMF 내장과 표시를 각각 검사한다. EMF 데이터 보존과 rhwp의 화면 렌더링은 별개 판정이다.
4. **동등성 및 성능 판정**
   - 짧은 전체 기능 원고와 대규모 원고를 기존 백엔드와 비교한다.
   - 구조·리소스·필드 검증과 실제 줄바꿈/페이지/각주 번호/표 분할/잘림 검증을 나눈다.
   - 템플릿 읽기, 생성, 조판, 저장, 검증 시간을 각각 측정한다. 속도 개선은 측정 전 단정하지 않는다.
5. **기본값 전환**
   - HWP 계약을 통과한 뒤 기본 백엔드 변경 여부를 판단한다. 미지원 구조는 명시적으로 실패한다.
   - 사용자에게 알리지 않는 COM 자동 fallback은 두지 않는다.
   - C# 백엔드의 HWPX 지원과 해당 런타임 안내는 유지한다. hwp2pdf도 별도 과제다.

## 가장 먼저 확인할 질문

현재 `templates/template.hwp`를 rhwp로 읽고 아무것도 수정하지 않은 채 저장한
파일이 한글에서 동일한 구조와 모양으로 열리는가? 시험에서 HWP→HWP는
본문·서식·필드와 19쪽의 픽셀이 일치했다. HWPX 관련 경로에서는 세로쓰기,
스타일 및 일부 필드 속성·페이지 배치 차이가 확인됐으나 HWPX는 지원 범위에서
제외했다. 이어 수행한 [최소 생성 시험](rhwp-generation-2026-10-20.md)에서도
평문 제목·본문·메타데이터의 구조와 한 페이지 픽셀이 일치했다.
이 결과를 아직 미지원인 복합 제목·개체 생성 성공으로 확대 해석하지 않는다.

## 빌드와 사용

```powershell
pwsh -NoProfile -File tools/development/build.ps1 -Configuration Debug
.\target\debug\md2hwp.exe 원고.md --worker .\target\debug\md2hwp-rhwp.exe
.\target\debug\md2hwp-rhwp.exe 원고.ir.json
```

일반 Debug·Release 빌드는 두 백엔드를 모두 만들며 ZIP에도 함께 넣는다. 기존 `-Rhwp`는 호환용 옵션으로 계속 허용한다. rhwp 실행에는 .NET/한글 COM이 필요하지 않으며, 이 worker와
`--dotnet`을 함께 지정하면 오류를 반환한다. Markdown을 IR로 바꾸는 단계에는
기존과 같이 Pandoc이 필요하다.
rhwp의 `init-template`과 `validate-template`도 한글·.NET 없이 실행할 수 있다.
아래의 템플릿 도구 설명과 검증 기록을 참고한다.

현재 지원 범위는 일반 문단, heading1–heading6의 평문·번호 문단 및 복합 제목 블록,
Text/Space/LineBreak, Strong/Emph/Link 표시 문구이다. 제목 블록에서는 표·글상자·머리말·
꼬리말의 여러 제목 슬롯, once/except.once, 중첩 each.child, own/ancestor 번호 태그와
쪽 나눔을 처리한다. 루트 정적 문단과 제목 블록 내부에서 meta 및 date-meta fmt를
치환한다. 기본 템플릿으로 제목·본문 원고를 생성한 비교 결과는
[제목 블록 시험](rhwp-headings-2026-10-21.md)에 기록한다.
원고의 글머리표·번호 목록은 본문 서식과 목록 샘플의 native 표식을 결합한다.
원고의 시작 번호, 중첩 들여쓰기, 하위 목록 뒤의 상위 번호 재개를 유지한다.
여러 문단 항목은 UseInstWidth=false의 기존 단위 계산과 UseInstWidth=true의
실제 표식 폭 측정을 모두 지원한다. 실제 폭은 문서 합성 후 native 번호 정의의
카운터·시작값·재개와 수준별 표시 형식을 해석하고, 표식 자체의 문자 서식으로
Windows GDI에서 측정한다. 설치된 TTF/OTF와 확인 가능한 글리프가 필요하며,
지원하지 않는 번호 형식·이미지/사용자 영역 글머리표·글꼴 대체는 명시적으로 거부한다.
기본 템플릿은 글머리표가 false, 번호 목록이 true이다. 긴 문장의 자동 줄바꿈은
여러 문단 항목과 별개이며 두 표식 모두 지원한다.
[이전 목록 시험](rhwp-lists-2026-10-21.md)은 당시 결과로 보존하며,
[표식 실측 구현과 검증 범위](rhwp-list-widths-2026-10-22.md)에 현재 계약을 기록한다.
코드 박스는 템플릿의 한 셀 표와 native 출처 캡션을 복제한다. 제목 슬롯이 있을 때의
`제목:` 처리, 원고 줄별 문단과 공백·탭·빈 줄, 여러 출처 문단, 앞뒤 빈 문단을 보존한다.
기본 템플릿의 긴 박스는 한글 백엔드와 rhwp 모두 페이지 아래로 잘릴 수 있다.
[박스 시험과 한계](rhwp-code-2026-10-21.md)를 참고한다.
그림은 PNG/JPG/JPEG/EMF 원본을 내장하며 템플릿의 native 캡션과 여러 출처 문단,
장별 자동번호 재시작을 지원한다. 샘플 그림의 이미지·크기를 무시하고 선언된 폭과
원본 비율로 생성한다. [그림 시험](rhwp-figures-2026-10-21.md)에 표시 비교와
JPEG 재인코딩 차이를 기록한다.
이 재인코딩에 따른 JPEG 표시 차이는 사용자 승인으로 동등성 판단에서 허용한다.
구조·배치·캡션과 다른 이미지 형식의 검증은 유지한다.
같은 확장자와 원본 파일 바이트의 그림은 내장 리소스를 공유하며, 그림별 개체·
크기·배치·캡션·번호는 독립적으로 유지한다. 서로 다른 파일을 픽셀 일치만으로
합치지 않는다. [이미지 리소스 공유 검증](rhwp-image-resources-2026-10-22.md)을 참고한다.
표는 템플릿의 머리행·본문행·병합 출처행과 native 캡션을 사용하고,
Windows GDI로 실제 TTF/OTF 글꼴을 측정해 열 폭을 계산한다. .NET과 COM은
사용하지 않으며 글꼴 대체와 HFT는 거부한다. 원래 표의 TreatAsChar·쪽 나눔·
머리행 반복 옵션을 유지한다. 추적 템플릿은 TreatAsChar가 켜져 있어 긴 표가
잘릴 수 있으며, 별도 기본 템플릿으로 페이지 나눔을 시험했다.
본문행이 있는 생성 floating 표는 rhwp 자체 조판으로 머리행 고립을 판정해
표 앞 쪽 나눔을 보정하고, 저장·재열기 후에도 확인한다. 원형의 글자처럼 취급
설정이나 본문 없는 머리행·출처 표는 변경하지 않는다. [통합 비교의 표 보정
검증](rhwp-integration-2026-10-22.md#3-표-머리행-고립-보정)은 실제 한글의 고립 사례와
보정 후 3쪽 일치를 기록한다. 두 조판 엔진의 모든 경계가 같다는 보장은 아니다.
[표 시험과 한계](rhwp-tables-2026-10-21.md)를 참고한다.
각주는 본문·제목·목록·표 셀과 여러 문단의 각주 본문을 지원한다.
첫 문단과 선택적 `footnote.next` 샘플의 서식·native AUTONUM·탭을 유지하며,
제목 슬롯이나 each.child 복제로 반복된 참조마다 독립 native 각주를 생성한다.
생성된 위치를 검사해 native 캡션·머리말·꼬리말·바탕쪽·주석·다른 각주 안의
참조는 거부한다. 저장된 AUTONUM 바이트 검증과 고정 파서의 파생 번호 캐시 비교를
구분하며, 번호의 실제 표시는 한글 페이지로 별도 확인한다.
[각주 시험](rhwp-footnotes-2026-10-22.md)에 최종 원고·추적 템플릿의 3쪽과 문서
각주 시작 7인 별도 native 샘플 템플릿의 1쪽 비교를 기록한다. 두 비교 모두 픽셀
차이가 없었으며, 저장 번호와 파서 캐시 검증은 구분한다. OnPage 재시작의 실제
표시는 당시 시험하지 않았다. 후속 [통합 비교](rhwp-integration-2026-10-22.md)에서는
OnPage 템플릿으로 양쪽 3쪽이 일치했고, 2쪽의 1–9 뒤 3쪽에서 1로 재시작함을
확인했다. 이는 한글에서 HWP를 열었을 때의 표시이며 rhwp 자체 조판의 보장은 아니다.
번호 상호참조는 기존 IR 0.4와 템플릿 선언으로 생성한다. 제목 참조는 여섯
`ref.headingN.number` 샘플과 원고 카운터로 계산한 고정 텍스트이며 native 개요
필드나 하이퍼링크를 만들지 않는다. HWP에서 제목을 직접 수정해도 자동 갱신되지 않는다.
그림·표 참조는 실제 대상의 native 식별자와 번호를 가리키는 Crossref 필드다.
앞쪽 참조를 포함해 대상이 확정된 뒤 표 열 폭을 다시 측정한다. 그림·표 참조의
폭은 한글 백엔드와 같은 보수적 예약값을 사용한다. 원형 조각의 자체 서식에 원고
강조·기울임을 적용하고 장 번호·개체 번호를 각각 999로 측정하며, 참조 전체를
나눌 수 없는 한 단위로 취급한다. 실제 표시 캐시의 짧은 번호로 폭을 줄이지 않는다.
본문·제목·목록·각주·표 셀과 개체 캡션·모든 출처 문단을 처리하며 원고의 참조
서식을 유지한다. 그림 alt는 대상을 검증하되 출력 필드를 요구하지 않는다.
[상호참조 시험](rhwp-references-2026-10-22.md)에서 23개 native 필드의 대상·캐시·
식별자를 독립 검사했고, 한글로 출력한 양쪽 5쪽의 픽셀 차이가 없었다. 원형 조각
서식에 따른 보수적 참조 예약 폭과 인접 필드 경계 보존을 적용한 결과다.
HWPX는 계속 명시적 미지원 오류다.
제목 블록의 그림·OLE·구역 정의는 한글 백엔드와 공통으로 거부한다.
조건부 문단 합치기는 native 필드의 시작·끝과 숨은 위치를 보존한다.
조건부 삭제가 필드의 한쪽 경계만 없애는 경우는 오류다.
엄격 검사와 조건부 필드 대조 및 남은 차이는
[기능 동등성 검토](rhwp-parity-2026-10-23.md)에 기록한다.
별도 `validate-template`은 원고의 사용 여부와 관계없이 모든 선언과 원형을 검사한다.
검사 범위와 한글 백엔드 대조 결과는 [템플릿 도구 검증](rhwp-template-tools-2026-10-22.md)에 있다.

저장은 임시 파일에 수행한 뒤 rhwp 재열기와 모델 비교를 통과해야 결과를 교체한다.
이 검사는 한글의 실제 페이지 배치와 시각적 동등성을 보장하지 않는다.

## 한글 없이 템플릿 검사·생성

```powershell
.\target\debug\md2hwp.exe validate-template templates/template.hwp --worker .\target\debug\md2hwp-rhwp.exe
.\target\debug\md2hwp.exe init-template 내템플릿.hwp --worker .\target\debug\md2hwp-rhwp.exe
.\target\debug\md2hwp-rhwp.exe validate-template 내템플릿.hwp
.\target\debug\md2hwp-rhwp.exe init-template 별도템플릿.hwp
```

경로는 생략할 수 있으며, 직접 실행에서도 `--template`·`--output`을
쓸 수 있다. 검사 경로의 기본값은 EXE 폴더의 `template.hwp`, 생성 경로의 기본값은
현재 작업 폴더의 `template.hwp`이다. 생성은 기존 경로를 덮어쓰지 않는다.
두 명령 모두 HWP만 지원하며 HWPX 경로는 한글 백엔드 사용을 안내하고 거부한다.

검사는 전체 문서의 메타데이터 문법·필수 키를 먼저 수집하고 모든 제목·목록·박스·
그림·표·각주·참조 원형, 선언 범위와 서식 참조를 확인한다. 빈 원고를 렌더링하는
검사가 아니므로 미사용 원형과 조건 분기도 검사한다. 원본은 변경하지 않는다.
출력 JSON 필드는 한글 백엔드와 같다. 실제 페이지 배치·글자 잘림은 별도 확인해야 한다.

생성은 명시적인 A4·함초롬바탕 10pt 기본 모델에서 시작하며, 기존 HWP 템플릿이나
upstream의 빈 문서 파일을 복사하지 않는다. 각 역할의 별도 편집 가능한 스타일과
현재 IR 0.4의 모든 필수 선언·native 표·그림 캡션·각주 샘플을 만든다.
임시 저장·재열기·독립 모델 대조·엄격한 템플릿 검사를 통과한 뒤 새 경로에 게시한다.
