# rhwp 백엔드 범위와 사용

rhwp 백엔드는 HWP·HWPX 템플릿과 HWP·HWPX 출력을 지원한다.
IR 0.4와 원고 문법, 템플릿 태그는 두 백엔드가 공유한다. 실제 생성·한글 재열기·
페이지 비교의 범위는 [통합 비교](rhwp-integration-2026-10-22.md)에 기록한다.

## 현재 배포와 자동 선택

현재 개발 빌드와 실행용 ZIP에는 `md2hwp-rhwp.exe`와 `md2hwp-hancom.exe`를 함께 넣는다. `--worker`를 생략하면 EXE 옆의 rhwp를 우선하고, 파일이 없을 때 한글 백엔드를 선택한다. 템플릿이나 출력이 `.hwpx`여도 같다. 명시한 `--worker`는 그대로 사용하며, 실행·검증 실패 후 다른 백엔드로 재시도하지 않는다. 한글 백엔드와 `hwp2pdf.exe`의 한글·.NET·보안 모듈 의존은 유지한다.

사용자는 현재 남은 템플릿·레이아웃 제한을 수용해 기본 선택 변경을 승인했다. 한글의 JPEG 재인코딩에 따른 관찰된 표시 차이는 허용한다. 이 결정은 임의 템플릿의 완전한 동등성이나 긴 박스·표의 잘림 안전성을 입증하지 않는다. [기능 동등성 검토](rhwp-parity-2026-10-23.md)와 아래 검증 기록의 범위를 유지한다.

## 구현 경계와 검증 원칙

`Markdown/Pandoc JSON → md2hwp IR → 템플릿 바인딩/생성 계획 → rhwp 어댑터 → HWP`

Pandoc 실행은 앱이, AST 해석과 IR 검증은 공유 코어가 담당한다. 공개 IR에 rhwp 타입을
노출하지 않으며, 어댑터가 검증된 IR을 native 문서 모델로 변환한다. 템플릿의 정적 영역과
미사용 서식을 보존하고 그림·표 번호, 각주와 개체 참조는 native 구조로 유지한다.
rhwp 라이브러리를 직접 링크하는 `md2hwp-rhwp.exe`는 기존 worker CLI와
IR+템플릿→출력 계약을 사용한다. 조합은 항상 HWP 모델에서 하며 HWPX는 파일 경계에서만 다룬다.

의존성은 upstream 릴리스 태그 `v0.9.1`의 커밋 `981ce66b4183b13c1a3b5907e04a8969c8c42034`에 고정한다.
새 릴리스나 devel의 최신 커밋을 따라가지 않고, 필요한 수정이 생겼을 때만 고정 커밋을 올린다.
[공개 모델·파서·저장 API](https://github.com/edwardkim/rhwp/blob/981ce66b4183b13c1a3b5907e04a8969c8c42034/src/lib.rs)의
존재만으로 임의 native 구조의 보존을 보장하지 않는다.
[MIT 라이선스](https://github.com/edwardkim/rhwp/blob/981ce66b4183b13c1a3b5907e04a8969c8c42034/LICENSE)의
저작권·허가문과 전이 의존성의 배포 고지를 보존한다.

저장·재열기 후 독립적으로 구성한 예상 모델과 구조·서식·리소스·필드 관계를 비교한다.
한글에서의 줄바꿈·페이지 배치·각주 번호·표 분할·잘림은 별도 시각 검증 대상이다.
백엔드의 구조 검사 통과를 시각적 동등성이나 PDF 품질 보장으로 확대하지 않는다.
`hwp2pdf`는 한글 자동화를 사용하는 별도 프로그램이다.

## 빌드와 사용

```powershell
pwsh -NoProfile -File tools/development/build.ps1 -Configuration Debug
.\target\debug\md2hwp.exe 원고.md --worker .\target\debug\md2hwp-rhwp.exe
.\target\debug\md2hwp-rhwp.exe 원고.ir.json
```

일반 Debug·Release 빌드는 두 백엔드를 모두 만들며 ZIP에도 함께 넣는다. 기존 `-Rhwp`는 호환용 옵션으로 계속 허용한다. rhwp 실행에는 .NET/한글 COM이 필요하지 않으며, 이 worker와
`--dotnet`을 함께 지정하면 오류를 반환한다. Markdown을 IR로 바꾸는 단계에는
기존과 같이 Pandoc이 필요하다.
rhwp의 `init-template`과 `validate-template`도 한글·.NET 없이 실행할 수 있다.
아래의 템플릿 도구 설명과 검증 기록을 참고한다.

## 지원 범위와 제약

현재 지원 범위는 일반 문단, heading1–heading6의 평문·번호 문단 및 복합 제목 블록,
Text/Space/LineBreak, Strong/Emph/Link 표시 문구이다. 제목 블록에서는 표·글상자·머리말·
꼬리말의 여러 제목 슬롯, once/except.once, 중첩 each.child, own/ancestor 번호 태그와
쪽 나눔을 처리한다. 루트 정적 문단과 제목 블록 내부에서 meta 및 date-meta fmt를
치환한다.
문서 끝의 빈 문단은 마지막 블록 종류와 관계없이 본문 샘플의 스타일·서식을 사용한다.
제목 블록 끝에서 넘어온 쪽 나눔은 이 본문 빈 문단에도 유지한다.
원고의 글머리표·번호 목록은 본문 서식과 목록 샘플의 native 표식을 결합한다.
원고의 시작 번호, 중첩 들여쓰기, 하위 목록 뒤의 상위 번호 재개를 유지한다.
여러 문단 항목은 UseInstWidth=false의 기존 단위 계산과 UseInstWidth=true의
실제 표식 폭 측정을 모두 지원한다. 실제 폭은 문서 합성 후 native 번호 정의의
카운터·시작값·재개와 수준별 표시 형식을 해석하고, 표식 자체의 문자 서식으로
Windows GDI에서 측정한다. 설치된 TTF/OTF와 확인 가능한 글리프가 필요하며,
지원하지 않는 번호 형식·이미지/사용자 영역 글머리표·글꼴 대체는 명시적으로 거부한다.
기본 템플릿은 글머리표가 false, 번호 목록이 true이다. 긴 문장의 자동 줄바꿈은
여러 문단 항목과 별개이며 두 표식 모두 지원한다.
[표식 실측 구현과 검증 범위](rhwp-list-widths-2026-10-22.md)에 현재 계약을 기록한다.
코드 박스는 템플릿의 한 셀 표와 native 출처 캡션을 복제한다. 제목 슬롯이 있을 때의
`제목:` 처리, 원고 줄별 문단과 공백·탭·빈 줄, 여러 출처 문단, 앞뒤 빈 문단을 보존한다.
기본 템플릿의 긴 박스는 한글 백엔드와 rhwp 모두 페이지 아래로 잘릴 수 있다.
그림은 PNG/JPG/JPEG/EMF 원본을 내장하며 템플릿의 native 캡션과 여러 출처 문단,
장별 자동번호 재시작을 지원한다. 샘플 그림의 이미지·크기를 무시하고 선언된 폭과
원본 비율로 생성한다. [통합 비교](rhwp-integration-2026-10-22.md)에 표시 비교와
JPEG 재인코딩 차이를 기록한다.
이 재인코딩에 따른 JPEG 표시 차이는 사용자 승인으로 동등성 판단에서 허용한다.
구조·배치·캡션과 다른 이미지 형식의 검증은 유지한다.
같은 확장자와 원본 파일 바이트의 그림은 내장 리소스를 공유하며, 그림별 개체·
크기·배치·캡션·번호는 독립적으로 유지한다. 서로 다른 파일을 픽셀 일치만으로
합치지 않는다. [이미지 리소스 공유 검증](rhwp-image-resources-2026-10-22.md)을 참고한다.
표는 템플릿의 머리행·본문행·병합 출처행과 native 캡션을 사용하고,
Windows GDI로 실제 TTF/OTF 글꼴을 측정해 열 폭을 계산한다. .NET과 COM은
사용하지 않으며 글꼴 대체와 HFT는 거부한다. 원래 표의 TreatAsChar·쪽 나눔·
머리행 반복 옵션을 유지한다. 추적 템플릿은 TreatAsChar가 켜져 있어 긴 표가
잘릴 수 있으며, 별도 기본 템플릿으로 페이지 나눔을 시험했다.
본문행이 있는 생성 floating 표는 rhwp 자체 조판으로 머리행 고립을 판정해
표 앞 쪽 나눔을 보정하고, 저장·재열기 후에도 확인한다. 원형의 글자처럼 취급
설정이나 본문 없는 머리행·출처 표는 변경하지 않는다. [통합 비교의 표 보정
검증](rhwp-integration-2026-10-22.md#3-표-머리행-고립-보정)은 실제 한글의 고립 사례와
보정 후 3쪽 일치를 기록한다. 두 조판 엔진의 모든 경계가 같다는 보장은 아니다.
각주는 본문·제목·목록·표 셀과 여러 문단의 각주 본문을 지원한다.
첫 문단과 선택적 `footnote.next` 샘플의 서식·native AUTONUM·탭을 유지하며,
제목 슬롯이나 each.child 복제로 반복된 참조마다 독립 native 각주를 생성한다.
생성된 위치를 검사해 native 캡션·머리말·꼬리말·바탕쪽·주석·다른 각주 안의
참조는 거부한다. 저장된 AUTONUM 바이트 검증과 고정 파서의 파생 번호 캐시 비교를
구분하며, 번호의 실제 표시는 한글 페이지로 별도 확인한다.
[각주 시험](rhwp-footnotes-2026-10-22.md)에 최종 원고·추적 템플릿의 3쪽과 문서
각주 시작 7인 별도 native 샘플 템플릿의 1쪽 비교를 기록한다. 두 비교 모두 픽셀
차이가 없었으며, 저장 번호와 파서 캐시 검증은 구분한다. OnPage 재시작의 실제
표시는 당시 시험하지 않았다. 후속 [통합 비교](rhwp-integration-2026-10-22.md)에서는
OnPage 템플릿으로 양쪽 3쪽이 일치했고, 2쪽의 1–9 뒤 3쪽에서 1로 재시작함을
확인했다. 이는 한글에서 HWP를 열었을 때의 표시이며 rhwp 자체 조판의 보장은 아니다.
번호 상호참조는 기존 IR 0.4와 템플릿 선언으로 생성한다. 제목 참조는 여섯
`ref.headingN.number` 샘플과 원고 카운터로 계산한 고정 텍스트이며 native 개요
필드나 하이퍼링크를 만들지 않는다. HWP에서 제목을 직접 수정해도 자동 갱신되지 않는다.
그림·표 참조는 실제 대상의 native 식별자와 번호를 가리키는 Crossref 필드다.
앞쪽 참조를 포함해 대상이 확정된 뒤 표 열 폭을 다시 측정한다. 그림·표 참조의
폭은 한글 백엔드와 같은 보수적 예약값을 사용한다. 원형 조각의 자체 서식에 원고
강조·기울임을 적용하고 장 번호·개체 번호를 각각 999로 측정하며, 참조 전체를
나눌 수 없는 한 단위로 취급한다. 실제 표시 캐시의 짧은 번호로 폭을 줄이지 않는다.
본문·제목·목록·각주·표 셀과 개체 캡션·모든 출처 문단을 처리하며 원고의 참조
서식을 유지한다. 그림 alt는 대상을 검증하되 출력 필드를 요구하지 않는다.
[상호참조 시험](rhwp-references-2026-10-22.md)에서 23개 native 필드의 대상·캐시·
식별자를 독립 검사했고, 한글로 출력한 양쪽 5쪽의 픽셀 차이가 없었다. 원형 조각
서식에 따른 보수적 참조 예약 폭과 인접 필드 경계 보존을 적용한 결과다.
이 기록 당시 HWPX는 미지원이었다.
제목 블록의 그림·OLE·구역 정의는 한글 백엔드와 공통으로 거부한다.
조건부 문단 합치기는 native 필드의 시작·끝과 숨은 위치를 보존한다.
조건부 삭제가 필드의 한쪽 경계만 없애는 경우는 오류다.
엄격 검사와 조건부 필드 대조 및 남은 차이는
[기능 동등성 검토](rhwp-parity-2026-10-23.md)에 기록한다.
별도 `validate-template`은 원고의 사용 여부와 관계없이 모든 선언과 원형을 검사한다.
검사 범위와 한글 백엔드 대조 결과는 [템플릿 도구 검증](rhwp-template-tools-2026-10-22.md)에 있다.

저장은 임시 파일에 수행한 뒤 rhwp 재열기와 모델 비교를 통과해야 결과를 교체한다.
이 검사는 한글의 실제 페이지 배치와 시각적 동등성을 보장하지 않는다.

## 한글 없이 템플릿 검사·생성

```powershell
.\target\debug\md2hwp.exe validate-template templates/template.hwp --worker .\target\debug\md2hwp-rhwp.exe
.\target\debug\md2hwp.exe init-template 내템플릿.hwp --worker .\target\debug\md2hwp-rhwp.exe
.\target\debug\md2hwp-rhwp.exe validate-template 내템플릿.hwp
.\target\debug\md2hwp-rhwp.exe init-template 별도템플릿.hwp
```

경로는 생략할 수 있으며, 직접 실행에서도 `--template`·`--output`을
쓸 수 있다. 검사 경로의 기본값은 EXE 폴더의 `template.hwp`, 생성 경로의 기본값은
현재 작업 폴더의 `template.hwp`이다. 생성은 기존 경로를 덮어쓰지 않는다.
두 명령 모두 `.hwpx` 경로를 받는다. 생성은 HWP로 검증한 모델을 HWPX로 내보내고, 그 HWPX를 다시 HWP로 내려 엄격 검사까지 통과해야 게시한다.

검사는 전체 문서의 메타데이터 문법·필수 키를 먼저 수집하고 모든 제목·목록·박스·
그림·표·각주·참조 원형, 선언 범위와 서식 참조를 확인한다. 빈 원고를 렌더링하는
검사가 아니므로 미사용 원형과 조건 분기도 검사한다. 원본은 변경하지 않는다.
출력 JSON 필드는 한글 백엔드와 같다. 실제 페이지 배치·글자 잘림은 별도 확인해야 한다.

생성은 명시적인 A4·함초롬바탕 10pt 기본 모델에서 시작하며, 기존 HWP 템플릿이나
upstream의 빈 문서 파일을 복사하지 않는다. 각 역할의 별도 편집 가능한 스타일과
현재 IR 0.4의 모든 필수 선언·native 표·그림 캡션·각주 샘플을 만든다.
임시 저장·재열기·독립 모델 대조·엄격한 템플릿 검사를 통과한 뒤 새 경로에 게시한다.

## rhwp 0.9.0 갱신 — 2026-11-11

고정 커밋을 `1a76570`(0.8.7)에서 `7213ed1`(0.9.0)로 올렸다. 어댑터에서 바꾼 것은 다음과 같다.

- 저장본 비교는 `DocumentCore`가 열면서 덧붙이는 파생 줄 정보가 아니라 저장된 레코드
  (`rhwp::parser::parse_hwp`)를 대상으로 한다. 빈 셀 문단의 줄 정보를 upstream 읽기 동작에
  맞춰 미리 합성하던 코드는 제거했다. 생성 문단은 줄 레코드를 저장하지 않는다.
- 조합 과정에서 비워진 문단은 `has_para_text`를 내린다. 0.9.0 저장기는 이 표지가 남으면
  빈 PARA_TEXT를 쓰고, 한글 2020은 그 파일을 열지 못한다. rhwp 재열기로는 드러나지 않는다.
- 수식 폭 추정은 새 수식 AST(중첩 글꼴 지정, 묶음·조합·왼쪽 첨자·긴 나눗셈 노드)를 이전과
  같은 모양으로 읽는다. 한글 실측 1,366건의 폭이 이전 버전과 모두 같다.
- 번호 정의는 10수준이 되었고 어댑터는 원고의 7수준만 다룬다. 영문 번호는 26까지만 실측한다.
- upstream이 수정된 svg2pdf를 직접 포함하므로 `dependencies/vendor/svg2pdf`와 루트 패치를 없앴다.

한글 2020 11.0.0.9136에서 150 DPI 페이지 이미지로 이전 버전 결과와 비교했다. 추적 템플릿의
예제 11종 56쪽, `init-template` 템플릿과 그 템플릿으로 만든 2종 9쪽이 모두 픽셀 단위로 같다.
저장 레코드에서 달라진 것은 생성 표의 개체 속성 비트 28(추적 템플릿 원형과 같아짐), 표 높이 값,
내장 PNG 미리보기의 압축 바이트다. 수식 예제와 긴 표·박스는 이번 비교에 넣지 않았다.

HWPX는 계속 미지원이다. 임시 시험 빌드로 본 결과는 이슈 #12의 근거로만 쓴다. HWPX 템플릿을
HWP로 내려 생성한 결과는 HWP 템플릿 결과와 13쪽 모두 같았고, HWPX 출력은 13쪽 중 7쪽이
같았으며 나머지 6쪽은 짝수 쪽 가로선 끝의 26픽셀 차이였다. 이전 버전의 세로쓰기 셀 손실과
각주 구분선 차이는 나타나지 않았다.

## upstream devel 고정 — 2026-11-12

고정 커밋을 `7213ed1`(main, 0.9.0)에서 devel의 `eb84afc`로 옮겼다. 바탕쪽 종류(양쪽·짝수·홀수)를
구역 속성 비트에서 읽고 쓰는 수정(`d7873c6`, upstream PR #8906)이 devel에만 있기 때문이다.
main은 devel과 갈라져 있어 이 수정을 포함하지 않는다. 고정 커밋은 `d7873c6` 이후여야 한다.

- 바탕쪽 조합 11건(HWP·HWPX)의 `dump`, `export-svg`, `export-hwpx`, `convert` 결과가 한글 2020의
  저장 값·쪽별 표시와 모두 같다. `7213ed1`에서는 7건까지 달랐다.
- 어댑터 코드는 바꾸지 않았다. 예제 13종을 `7213ed1` 결과와 비교하면 11종은 바이트까지 같고,
  2종은 생성 표의 높이 값 하나만 다르다(4160 → 5440). 한글 2020의 150 DPI 쪽 이미지 165쪽은 모두 같다.
- 수식 예제와 HWPX 출력 경로는 이번 비교에 넣지 않았다.
- 떠 있는 표의 머리행·첫 본문 행 쪽 넘김 검사는 저장한 뒤 다시 연 문서의 쪽 배치로 한다. rhwp 0.9는 파일을
  열 때만 줄 배치를 만들어, 메모리의 조합 모델과 저장본의 쪽 나눔이 달라질 수 있다. `init-template` 템플릿과
  전체 기능 원고에서 저장 전 검사는 통과하고 재열기 검사가 실패하던 것을 이 방식으로 고쳤다. 이전 고정 커밋
  `1a76570`(0.8.7)에서는 생기지 않았다.

고정 커밋을 올릴 때는 `Cargo.lock`, 제3자 고지, 예제의 한글 쪽 이미지 비교를 함께 갱신·확인한다.

고정 커밋을 `eb84afc`에서 devel의 `e4f8ff2`로 옮겼다(356커밋). HWPX를 HWP로 내릴 때 바탕쪽 종류가

- 어댑터 코드는 바꾸지 않고 빌드·테스트를 통과했다.
- 예제 14종의 HWP 출력은 `eb84afc` 결과와 바이트가 다르다. 저장된 레코드를 비교하면 차이는 두 가지다.
  rhwp가 저장 파일에 자체 스트림 `RhwpLineSegTags`(40바이트)를 더하고, 생성한 표의 높이를 조판 값으로
  고쳐 쓰지 않아 어댑터가 넣은 값(셀 1, 표는 행 수)이 그대로 남는다. 표 개체 속성의 28번 비트도
  켜지지 않는다.
- 한글 2020에서 예제 4종(`tables`, `caption-references`, `all-features`, `footnotes`)을 PDF로 내보내
  비교하면 21쪽 모두 `eb84afc` 결과와 픽셀까지 같다. 나머지 예제와 HWPX 출력은 한글에서 열어 보지 않았다.

## 표 쪽 넘김 검사의 검사용 사본과 부분 읽기 — 2026-11-23

떠 있는 생성 표의 머리행 고립 보정은 쪽 나눔마다 문서 전체를 다시 구성·저장·재열기했다. 이제 구성한 문서를
한 번 저장해 파싱한 검사용 사본에서 찾는다(사본은 출력하지 않는다). 사본은 구역을 모델에서 다시 써서 열고,
쪽 나눔은 뒤를 모두 밀기 때문에 나눔마다 그 뒤를 다시 읽는다. 다만 쪽 나눔 뒤는 새 쪽에서 시작하므로 앞부분은
다시 읽지 않는다(`backends/rhwp/src/page_window.rs`).

- 사본 전체를 한 번 읽고 첫 고립을 찾는다. 그 뒤로는 창을 읽는다. 창은 사본의 구역 정의 문단과 마지막 쪽 나눔부터의
  뿌리 문단이며, 다음 후보 표 하나까지, 고립이 없으면 같은 시작점에서 다음 2, 4, 8개 후보까지 늘린다.
- rhwp는 그림·표·수식 번호와 각주 본문 번호를 문서 순서로 다시 세고, 쪽 번호도 처음부터 센다. 창은 쪽 나눔
  자리의 계수와 쪽 번호로 시작한다. 사본은 저장된 DocInfo를 그대로 쓰므로 각주·미주 시작 번호는 문서 속성이
  아니라 구역 정의 문단의 새 번호(NEWNUM)로 넣는다. 창마다 번호·목록 표지가 사본 전체 읽기와 같은지, 쪽 나눔
  쪽의 번호가 맞는지, 앞 쪽에서 넘어온 개체·각주가 없는지 확인한다.
- 구역 정의 문단이 첫 문단이 아니거나 다단, 본문 쪽 번호 필드, 미주가 있거나 rhwp의 모양 비율 허용치
  (`uses_hwp3_origin_page_tolerance`)가 켜진 문서는 창을 쓰지 않는다. 생성 문서는 문단마다 모양이 늘어
  비율이 0.45/0.60(문단/글자)이라 꺼져 있다.
- 마지막 창 뒤에 모든 쪽 나눔을 넣은 사본을 한 번 통째로 읽어 확인한다. 창을 쓸 수 없거나 이 확인이 실패하면
  사본을 처음 상태로 되돌리고 통째 읽기로 다시 보정한다. 찾은 쪽 나눔은 `set_document` 한 번으로 문서에 넣는다.
  저장한 출력은 다시 열어 구조 검사를 모두 하지만 그 rhwp 배치는 다시 읽지 않는다.
- `init-template` 템플릿 예제 6종(`all-features`, `object-sources`, `footnotes`, `metadata`, `layout-issues`,
  `large-5x`)과 `large-5x` 2·4배 원고의 HWP가 이전 커밋(`e4a3f39`)과도, 사본에서 차례로 읽던 `c93ea1`과도
  바이트까지 같다. Release 작업기 1회: 4배 23.5초(`c93ea1` 33.6초, `e4a3f39` 5회 중앙값 46.4초).
- 바이트가 같으므로 한글에서 다시 열어 보지 않았다. 창의 확인은 쪽 나눔마다 그 나눔이 꼭 필요했는지까지
  증명하지는 않는다. 근거는 위 바이트 비교다.

## 검사용 사본의 캡션 대체 — 2026-11-19

rhwp가 배치에서 빠뜨리는 캡션은 검사용 사본에서 같은 높이로 바꾼다. 바꾸기는 사본을 만들 때 한 번만 하고,
창과 통째 읽기는 바꾼 사본을 읽는다. 높이는 캡션 문단을 캡션 폭의 본문 문단으로 rhwp가 조판한 높이에서 마지막
캡션 줄의 줄 간격과 문단 아래 간격을 뺀 값에 캡션 간격을 더한 것이다. 한글 2020은 10 pt·160% 한 줄 캡션
문단 넷과 캡션 간격 283 HU인 그림 줄을 26835 + 283 + 4 × 1000 + 3 × 600 = 32918 HU로 저장한다. 그림과 표의
대체는 각각 따로 되돌릴 수 있는 커밋에 두었다. rhwp가 그 캡션을 배치에 넣게 되면 그 커밋만 되돌리고, 둘 다
되돌리면 이 측정도 지운다.

## 떠 있는 표의 위 캡션 — 2026-11-20

한글은 떠 있는 표의 앵커 줄 자리에 위 캡션을, 그 아래에 표를 둔다. 한글 2020이 다시 저장한 `large-5x`에서
다음 문단은 앵커 13083 + 283 + 1000 + 표 9600 = 23966 HU에 있고, 표가 다음 쪽으로 가면 캡션도 함께 넘어가 그
쪽의 다음 문단이 1283 + 9600 = 10883 HU에 온다. rhwp 0.9.1은 두 경우에 이 캡션을 빠뜨린다. 일반 문단 뒤 쪽
중간에 오는 표나 앞 쪽에서 쪽 나눔으로 넘어간 표의 캡션은 제대로 센다.

- **앞 쪽이 차서 쪽 첫머리로 넘어간 표:** 캡션 아래에 표를 그리지만 쪽 배치 위치는 표 높이만큼만 나아간다.
  그 쪽의 다음 표 캡션이 앞 줄을 덮고(`large-5x` 17쪽 표 158 다음의 표 160), 쪽 끝 표는 캡션과 머리행이 들어갈
  자리가 없어도 머리행만 그 쪽에 남긴다. 시험: 본문 39줄 뒤 표(머리행 + 3행), 본문 37줄, 표 → rhwp는 둘째 표의
  머리행을 2쪽에 남기고 한글은 표를 통째로 3쪽에 둔다.
- **셀에 각주가 있는 표:** 표 각주 높이(`large-5x`에서 24.7 px)를 미리 뺀 자리에 앵커 줄이 들어가지 않으면
  `prepare.rs`의 첫 행 이월 판정이 위 캡션을 빼지 않은 남은 자리로 머리행을 잰다. 그래서 캡션과 머리행
  (30.4 px)이 들어가지 않는 자리에도 머리행만 남긴다. 행 예산은 0이지만 rhwp는 첫 조각에 행을 하나 넣는다.
  `large-5x`의 표 190, 223, 292, 324(앵커 851.1 px, 남은 자리 25.7 px)가 이 경우이고, 캡션 글자를 10 pt에서
  50 pt까지 키워도 쪽 배치가 그대로였던 것도 이 때문이다. 시험: 본문 38줄 뒤 표(남은 자리 23.5 px) → 각주가
  없으면 rhwp도 표를 2쪽으로 넘기고, 첫 본문 칸에 각주가 있으면 머리행을 1쪽에 남긴다. 한글은 두 경우 모두
  표를 통째로 2쪽에 둔다.
- 두 시험 문서의 한글 2020 96 DPI 쪽 이미지를 보았다. 테스트가 두 경우의 rhwp 배치와 검사용 사본의 결과를
  고정하므로, 둘 다 실패하면(고정 버전이 두 캡션을 모두 세면) 이 커밋을 되돌린다. 한쪽만 고쳐졌으면 간격
  문단이 남은 쪽을 계속 막으므로 그대로 둔다.

검사용 사본은 이 캡션을 간격 문단으로 바꿔 두 경우를 함께 막는다. 바꾸기는 사본을 만들 때 한 번만 한다.

- 구역 정의가 있는 첫 문단 뒤의 이런 캡션을 앵커 앞의 간격 문단으로 바꾼다. 간격 문단은 줄 간격을 캡션 간격 +
  캡션 높이로 고정하고(rhwp는 비율이 아닌 줄 간격을 HWPUNIT 두 배로 저장한다), 캡션의 글자 모양으로 한 글자를
  담아 빈 줄 감추기에 걸리지 않게 한다. 앵커의 쪽·단 나눔과 머리행 고립 보정은 사본에서 간격 문단에 둔다. 첫
  문단의 표는 늘 첫 쪽 맨 위에 있고 rhwp가 그 캡션 자리를 잡으므로 그대로 둔다.
- 표의 첫 행이 간격 문단보다 뒤 쪽(단)에서 시작하면 간격 문단에도 나눔을 넣는다. 한글이 캡션을 표와 함께 넘기는
  것을 흉내 낸 것이라 출력 문서에는 넣지 않는다. 간격 문단과 앵커는 문서 순서대로(간격 문단이 그 표보다 먼저) 한
  줄로 정하고, 앞의 나눔을 넣은 배치에서 판정한다. 창도 이 순서를 그대로 따른다.
- 위 여백이나 세로 오프셋으로 바꾸는 방법도 시험했다. 위 여백은 rhwp가 이어지는 쪽마다 다시 넣고, 세로 오프셋은
  표가 다음 쪽으로 넘어가면 빠져서 둘 다 한글과 어긋났다.
- `init-template` 템플릿 예제 6종과 `large-5x` 2·4배 원고의 HWP가 이전 커밋과, 원래 커밋(`7d929f8`) 작업기
  결과와 바이트까지 같다. Release 작업기 1회: `large-5x` 4.4초(`7d929f8` 5.8초), 2배 11.8초(18.7초), 4배
  28.6초(66.4초).

## 글자처럼 취급하는 그림의 캡션 — 2026-11-19

rhwp 0.9.1은 글자처럼 취급하는 그림의 줄 높이를 그림만으로 잡고 캡션을 줄 밖에 그린다. 한글은 그림, 캡션
간격, 캡션 문단을 한 줄에 넣는다. `init-template` 템플릿 `all-features` 3쪽 첫 그림(캡션 4문단)의 줄은 한글
2020 저장값으로 32918 HU이고 rhwp는 26835 HU로 잡았다. 그래서 rhwp는 3쪽에 표 4-3과 캡션 없는 표(`점검`/
`문단 복귀`)의 머리행까지 넣고 본문 행을 4쪽으로 넘겨 머리행 고립으로 보고 쪽 나눔을 넣었다. 한글은 표 4-3부터
4쪽에 두고 표를 나누지 않는다.

- 검사용 사본을 만들 때 한 번, 위·아래 캡션이 있는 그림마다 캡션을 빼고 그 높이(캡션 간격 + 캡션 문단)만큼
  그림을 키운다. `all-features` 그림 8개 가운데 한글 저장값과 비교할 수 있는 6개(32918, 28118, 25529, 23929,
  23929, 34673 HU)가 계산값과 같다. 왼쪽·오른쪽 캡션은 그대로 둔다.
- rhwp가 캡션을 줄에 넣게 되면 테스트가 실패하므로 그때 이 커밋을 되돌린다.
- 표 캡션 대체와 함께 넣은 상태의 결과(원래 커밋 `d0c0ed4`에서 한글로 확인한 것):
  - `init-template` 템플릿 `all-features`: 쪽 나눔이 없어지고 한글 2020 100 DPI 쪽 이미지가 8쪽이다(전에는
    9쪽). 같은 템플릿에서 1–7쪽은 `v0.6.1`(main 고정 `1a76570`) 작업기 결과와 픽셀까지 같고, 8쪽은 두 번째
    별행 수식 아래가 1 px 내려간 차이뿐이며 이 차이는 이전 출력에서 쪽 나눔만 지워도 같다. 이전의 빈 9쪽은
    쪽 나눔 때문에 8쪽이 각주 9)까지 꽉 차 템플릿의 마지막 빈 본문 문단이 넘어간 것이다.
  - `large-5x`: 쪽 나눔이 없고 HWP가 이 수정 전과 바이트까지 같다(한글 79쪽). 그림 캡션만 대체하면 표 4개
    (문단 190, 223, 292, 324)에 쪽 나눔이 들어가지만 한글에서는 아무것도 바꾸지 않는다(17–41쪽 이미지가
    픽셀까지 같다). 표 캡션 대체가 이 넷을 없앤다.
- 이 커밋을 검사용 사본·부분 읽기 위에 옮긴 결과는 예제 6종과 `large-5x` 2·4배 원고 모두 원래 커밋(`d0c0ed4`)
  작업기 결과와 바이트까지 같다(`all-features`와 2·4배는 쪽 나눔이 달라져 `e4a3f39`와는 다르다). 그래서 한글에서
  다시 열어 보지 않았다. Release 작업기 1회: `large-5x` 5.8초(`d0c0ed4` 11.9초), 2배 11.1초(35.8초), 4배
  23.6초(120.8초).

## HWPX 지원 — 2026-11-12

rhwp 백엔드가 `.hwpx` 템플릿과 `.hwpx` 출력을 받는다(이슈 #12). 조합 코드는 바꾸지 않았고
HWPX는 `backends/rhwp/src/hwpx.rs`의 파일 경계에서만 다룬다.

- **HWPX 템플릿**: rhwp로 읽어 HWP로 내린 뒤, 내린 모델과 다시 읽은 HWP를 upstream의 변환 비교로
  대조하고 내장 데이터 바이트가 원본과 같은지 확인한다. 이후 과정은 HWP 템플릿과 같다.
- **HWPX 출력**: 기존 HWP 저장·재열기 검증을 모두 마친 뒤 그 HWP를 HWPX로 내보낸다. 저장한 HWPX를
  다시 열어 upstream의 내보내기 비교, 패키지 구조 검사, 내장 데이터 바이트, 쪽수, 수식 번호 범주를
  그 HWP와 비교하고, 통과해야 기존 출력을 교체한다.
- **`init-template`·`validate-template`**: `.hwpx` 경로를 받는다. 생성한 HWPX는 다시 HWP로 내려
  엄격 검사를 통과해야 게시한다.
- **자동 선택**: HWPX여도 rhwp를 우선한다. 한글 백엔드는 rhwp가 없거나 `--worker`로 지정할 때 쓴다.

HWPX 템플릿을 HWP로 내릴 때 바탕쪽 종류(양쪽·짝수·홀수)와 내용은 그대로 남고 순서만 HWP 저장 순서로
바뀐다(upstream 이슈 #9046, `e4f8ff2`에서 수정되어 `v0.9.1`에 포함). 한글 2020이 만든 바탕쪽 조합 11건을 내린
결과는 한글이 같은 HWPX를 HWP로 저장한 것과 종류·내용이 모두 같다. 어댑터는 종류를 고치지 않고,
내린 모델이나 다시 읽은 HWP의 종류가 원본과 다르면 실패한다.

고정 커밋의 변환이 한글 2020과 다른 한 곳은 어댑터가 바로잡고 재열기 후 확인한다.

- HWPX 저장기는 모든 수식에 `numberingType="EQUATION"`을 적는다. 한글은 본문 속 수식까지 번호를
  매겨 수식 번호가 밀린다. 저장된 패키지에서 이 속성만 모델 값으로 고쳐 쓰며, 수식은 인스턴스
  ID로 찾는다.

한글 2020 11.0.0.9136에서 150 DPI 쪽 이미지로 비교했다. 예제 13종과 수식 원고 1종을 추적 템플릿(HWP)과
그 템플릿을 한글이 HWPX로 저장한 템플릿으로 각각 HWP·HWPX 출력해 56개 파일을 만들었다. 모두
한글에서 열리고, HWP 템플릿→HWP 출력을 기준으로 한 나머지 세 조합 42건 501쪽이 모두 픽셀 단위로 같다.
rhwp `init-template`의 HWP·HWPX 템플릿(각 2쪽)과 그 템플릿으로 만든 전체 기능 원고(각 6쪽)도 같다.

확인하지 않은 것: 한글이나 rhwp가 저장하지 않은 HWPX 템플릿, 한글 외 뷰어의 표시, 한글 백엔드 결과와의 HWPX 비교. 변환행렬 계수는 HWPX를 거치며
단정밀도로 저장되는데(한글의 HWPX 저장도 같다) 이번 예제에서는 표시 차이가 없었다.
