# EMF 그림 입력과 표시 검증

독립 그림 문단에서 `.emf` 파일을 사용할 수 있습니다. 확장자는 대소문자를 구분하지 않습니다.

```markdown
![그림 설명](diagram.emf){#diagram}

출처: 작성기관

주.1: 추가 설명
```

IR 0.4의 기존 그림 경로를 사용하므로 IR·템플릿 선언을 추가할 필요가 없습니다.
캡션·장 번호·그림 자동번호·출처 여러 문단·상호참조는 기존 그림과 동일하게 처리합니다.
프로그램은 원본 파일을 한글 `InsertPicture`에 내장하며 PNG로 변환하지 않습니다.

## 크기와 입력 검사

템플릿의 `figure.max-width-mm`를 가로 폭으로 사용하고,
EMF 헤더 `rclFrame`의 가로·세로 차이에서 종횡비를 구합니다.
프레임은 0.01mm 단위입니다. `rclBounds`는 장치 단위이므로 픽셀 수로 사용하지 않습니다.
원점이 0이 아닌 프레임도 허용하지만 폭·높이가 0 또는 음수이면 거부합니다.
물리적 프레임이 잘못됐을 때 다른 크기로 조용히 대체하지 않습니다.
[Microsoft 헤더 명세](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/ns-wingdi-enhmetaheader)

COM 실행 전에 백엔드에서 다음을 검사합니다.

- EMR_HEADER, EMF 서명, 버전 1.0과 헤더 길이
- 실제 파일과 선언된 바이트·레코드 수의 일치
- 레코드 길이·4바이트 정렬·파일 경계, 중복 헤더와 최종 EMR_EOF
- 헤더 설명·EOF 팔레트 범위와 EOF 크기
- 파일 크기 최대 64 MiB, 레코드 최대 100만 개

고정 크기의 헤더와 레코드 경계만 읽으므로 전체 파일을 메모리에 올리지 않습니다.
이 검사는 컨테이너 검사이며, 모든 그리기 명령의 내부 데이터나 의미를 검증하는 완전한 EMF 해석기는 아닙니다.
실제 그리기 명령의 지원은 설치된 한글에 의존합니다.

## 재현용 원고와 그림

[시험 원고](../examples/emf/emf.md)는 일반 EMF·EMF+ Dual·EMF+ Only를 각각 두 번 사용합니다.
서로 다른 장에서 같은 파일을 재사용하며, 출처 여러 문단과 본문·출처·각주의 번호 참조도 확인합니다.
[생성 스크립트](../examples/emf/generate.ps1)는 Windows GDI+로 동일한 그림을 기록합니다.
선·점선·도형·한글 텍스트·클리핑·회전·반투명 겹침·비트맵을 포함합니다.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\examples\emf\generate.ps1 -Directory .\artifacts\emf-fixtures
.\target\release\md2hwp.exe .\examples\emf\emf.md
```

생성 스크립트는 지정한 폴더에 EMF와 300·600dpi GDI+ 기준 PNG를 만듭니다.
기록 장치에 따라 헤더·바이트가 달라질 수 있으므로 아래 검증은 커밋된 그림의 해시를 기준으로 합니다.

| 파일 | 종류 | SHA-256 |
| --- | --- | --- |
| EmfOnly.emf | 일반 EMF | `563C888D11A459D103397E0422B4AA9B685E2DC965402C85D361C7975CA517B8` |
| EmfPlusDual.emf | EMF+ Dual | `90AB4F7F8B705AB0B42AF0E28FF4B889F2AECBC90D33FC3F1763CA5FB6611426` |
| EmfPlusOnly.emf | EMF+ Only | `626AF2523A95B9806AE5CA84C82971560DAA854F2C3E89E0B519E3EC0ED7E29C` |

## 한글 외 렌더링과 픽셀 검토

검증 환경은 Windows x64, 한글 2020 `11.0.0.9136`, Windows GDI+, 맑은 고딕입니다.
세 종류 모두 원본을 내장한 후 저장·재열기했고, 이 세 파일에서는 내장 EMF의 바이트도 원본과 일치했습니다.
모든 EMF에서 원본 바이트가 보존된다는 보장은 하지 않습니다.

동일 원본을 직접 GDI+로 렌더링한 결과와 한글 `CreatePageImage`의 무손실 24비트 BMP를
300·600dpi에서 비교했습니다. PDF의 개체 좌표를 페이지 크기에 맞춰 변환하여 그림 영역을 잘랐고,
그림 내용에 맞춘 이동·확대·축소로 차이를 없애지 않았습니다.
기준 이미지·한글 이미지·차이 이미지와 영역별 확대 비교를 보관했습니다.

- 일반 EMF: 평균 채널 절대 차이 300dpi **4.305/255**, 600dpi **5.076/255**
- EMF+ Dual·Only: 각각 300dpi **4.775/255**, 600dpi **4.885/255**
- 픽셀은 완전히 같지 않습니다. 외곽·색 경계에는 수 픽셀의 위치·크기 차이가 있으며,
  글자 가장자리·점선·비트맵 보간도 다릅니다. 차이 이미지를 판정에서 제외하지 않았습니다.
- 확대 검토한 선·한글·클리핑·회전·반투명 겹침·비트맵은 모두 표시됐습니다.
  EMF+ 겹침 영역은 기준과 같은 RGB `(128, 0, 127)`을 포함했습니다.
- 일반 EMF의 반투명 영역에는 점무늬가 나타납니다. GDI+ 기준에도 동일한 표현이 있으므로
  한글이 새로 만든 투명도 오류로 분류하지 않았습니다. EMF+ 기준과도 구분해야 합니다.
- 한글 PDF 내보내기는 그림을 600dpi 래스터와 JPEG로 표현했습니다.
  PDF 압축·보간 차이를 원본 EMF 손상과 혼동하지 않도록 무손실 페이지 이미지도 검사했습니다.

GDI+는 한글 외에서 직접 호출한 비교 경로입니다. 한글 내부에서도 Windows 그리기 구현을 사용할 수 있으므로,
완전히 독립된 해석 엔진 두 개의 일치나 모든 EMF의 표시 정확성을 입증한 검사는 아닙니다.
LibreOffice는 사용하지 않았습니다.

## 생성 방식 비교와 검증 결과

같은 시험 원고로 Debug 기본 XML, Debug 레거시 COM, Release XML 문서를 생성했습니다.
모두 IR 0.4, EMF 그림 6개, 각주 1개, 9쪽이며 원고·템플릿을 변경하지 않았습니다.
템플릿의 기존 첫 빈 페이지도 비교에 포함했고, EMF 지원에서 페이지 나눔을 수정하지 않았습니다.

세 쌍 모두 독립 비교기에서 구조·서식·참조·내장 데이터가 일치했고,
같은 Poppler 설정의 144dpi 전체 9쪽 RGB 픽셀도 일치했습니다.
이는 생성 방식끼리의 일치입니다. 위 GDI+와 한글 사이의 픽셀 차이까지 없다는 뜻은 아닙니다.
시험 환경의 단일 생성 시간은 Debug XML 11.205초, Debug COM 24.583초, Release XML 11.651초였습니다.
시간은 환경·캐시에 영향을 받으므로 EMF 전체 처리 속도를 보장하는 수치는 아닙니다.

Rust workspace 테스트·Clippy와 Debug·Release 백엔드 계약 검사를 통과했습니다.
그림 경로의 IR 왕복, 물리적 프레임·비영점 원점·정수 오버플로 방지,
손상된 헤더·길이·레코드·EOF와 자원 제한을 검사했습니다.
[검증 집계](emf-verification.json)에 입력 해시·환경·픽셀 차이·세 방식 비교 결과를 보관합니다.

원시 HWP·XML·PDF·BMP·PNG·차이·확대 비교·실행 로그는 ignored
`artifacts/emf-2026-10-09/`에 있습니다. 입력·경계 계약과 크기 계산 검사는
[백엔드 검사](../tests/backend-contract/EmfDimensionsTests.cs)에 유지합니다.


## PostScript 출력 추가 검토

Microsoft PS Class Driver에서 일반 EMF와 EMF+의 실제 PS 파일을 출력하고,
별도 PS 해석기로 전체 페이지와 서체를 확인했습니다. 벡터·글자 명령과 비트맵이
혼합되며 일부 글자는 래스터화됩니다. 시험한 이미지 압축은 Flate이고 JPEG는 없었습니다.
세부 조건·실측 수치·페이지 이미지는 [PostScript 검토](emf-postscript-review.md)를 참조하십시오.
