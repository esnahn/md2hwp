# 수식의 IR 표현 설계 (IR 0.6)

상태: core, Hancom 백엔드, rhwp 백엔드 구현. core는 Markdown 수식을
`inline_math`·`display_math`로 변환·검증한다. 두 작업기 모두 수식을 생성한다.
Hancom 작업기는 한글이 직접 조판한 크기를 쓰고, rhwp 작업기는 한글 실측에 맞춘
계산기로 크기를 추정한다(아래 "rhwp 작업기 구현"). 목록 항목 안의 별행 수식은
두 작업기 모두 거부한다.
`crates/md2hwp-math`의 TeX ↔ 한글 수식 SCRIPT 변환기를 문서 생성에
연결하기 위한 IR·템플릿·백엔드 계약을 정리한다.

## 결정 요약

| 항목 | 인라인 `inline_math` | 블록 `display_math` |
|---|---|---|
| 원고 | `$...$` | 문단 전체가 `$$...$$` 하나 |
| IR | `{"type":"inline_math","script":…}` | `{"type":"display_math","script":…}` |
| 글꼴 | 기본 수식 글꼴 | 기본 수식 글꼴 |
| 수식 편집기 글자 크기 | 속한 문단 스타일의 글자 크기 | 템플릿 `display_math.fontsize-pt` |
| 문단 서식 | 원래 문단 그대로 | 템플릿 표본 문단의 스타일 |
| 번호 종류 | 없음 | 수식 |
| 템플릿 선언 | 없음 | `display_math.fontsize-pt`, `begin/end:display_math`, `slot:display_math` |

## 이름

IR 타입 이름은 Pandoc의 `InlineMath`·`DisplayMath`를 따른다. 블록 수식의 템플릿
선언도 IR과 같은 `display_math`를 쓴다.

## IR에 SCRIPT를 담는 이유

core가 AST2IR 단계에서 Pandoc `Math`의 TeX를 `tex_to_hml_with_display`로
변환하고, IR에는 검증된 한글 수식 SCRIPT만 담는다.

- C# Hancom 백엔드는 Rust 변환기를 쓸 수 없다. SCRIPT를 담으면 두 백엔드가
  같은 문자열을 EQUATION 컨트롤에 넣기만 한다.
- "백엔드는 검증된 IR을 소비한다"는 원칙에 맞다. 지원하지 않는 TeX는 원고
  위치와 함께 IR 생성 전에 거부한다.
- 변환 결과가 인라인/별행에 따라 다르므로 그 정보를 가진 core에서 변환한다.
- 두 작업기의 IR 입력 검증은 같은 최소 검사만 한다. SCRIPT가 비어 있지 않고
  NFC이며 제어 문자가 없는지와 글자 수 한도만 확인하고 문법은 파싱하지 않는다.
  `md2ir`로 만든 IR을 고쳐 작업기에 넣으면 SCRIPT 문법 오류는 생성 단계에서 드러난다.

TeX 원문은 IR에 담지 않는다. 두 표현을 함께 두면 일치 검증이 변환기 버전에
묶인다. 글꼴·크기·정렬·번호 같은 표시 속성도 IR에 담지 않는다.

## IR 형식

### 인라인 `inline_math`

```json
{"type":"paragraph","inlines":[
  {"type":"text","value":"넓이는"}, {"type":"space"},
  {"type":"inline_math","script":"pi r^2"},
  {"type":"text","value":"이다."}]}
```

`script`는 비어 있지 않은 문자열이다. 제어 문자는 거부한다.
`Strong`/`Emph` 안에 있어도 허용하지만 수식에 글자 서식을 적용하지 않는다.
SCRIPT 자체의 `rm`·`it`·`bold`가 서식을 정한다.

### 블록 `display_math`

```json
{"type":"display_math","script":"sum _{k=1} ^{n} k = {n(n+1)} over {2}"}
```

Pandoc은 `$$...$$`를 `Para` 안의 `DisplayMath` 인라인으로 준다. 문단의
내용이 공백·줄바꿈을 제외하고 `DisplayMath` 하나뿐일 때만 블록으로 바꾼다.
`DisplayMath`가 다른 글과 섞인 문단은 1차 버전에서 거부한다.
`id`와 수식 상호참조는 두지 않는다. `$$ $$ {#eq:x}`는 pandoc-crossref 문법이며
현재 입력 형식에서 동작하지 않는다. 원고 문법을 정한 뒤 별도로 추가한다.

## 허용 위치 (1차)

| 위치 | 인라인 `inline_math` |
|---|---|
| 본문 문단, 목록 문단, 각주 본문 | 허용 |
| 제목 | 보류: 제목 블록 복제, 머리말·꼬리말 복사, 고정 제목 참조와 얽힘 |
| 표 셀 | 보류: 열 너비 계산이 Windows 글꼴 측정 기반이라 수식 폭을 잴 수 없음 |
| 캡션·출처·링크 라벨·그림 대체 텍스트 | 거부 |

블록 `display_math`는 IR에서 최상위 블록과 목록 항목 안에서 허용한다. 현재 두
작업기는 목록 항목 안의 별행 수식을 지원하지 않고 명시적으로 거부한다.
허용하지 않는 위치는 명시적으로 거부한다.

## 템플릿 선언

```text
{{md2hwp:display_math.fontsize-pt:11}}
{{md2hwp:begin:display_math}}
{{md2hwp:slot:display_math}}<탭>(<수식 AUTONUM>)
{{md2hwp:end:display_math}}
```

| 선언 | 구분 | 내용 |
|---|---|---|
| `display_math.fontsize-pt:값` | 필수 설정 | 블록 수식의 수식 편집기 글자 크기(pt). 양의 십진수, 소수점은 `.`. `begin:display_math` 앞의 독립 문단 |
| `begin:display_math` / `end:display_math` | 필수 | 일반 문단 하나를 감싸는 독립 경계 문단 |
| `slot:display_math` | 필수 | 경계 안 문단에 하나. 그 자리에 글자처럼 취급하는 수식 개체를 넣음 |

- 원고에 블록 수식이 없어도 선언은 필요하다. 다른 역할과 같은 규칙이다.
- 표본 문단에는 일반 글자와 탭을 슬롯 앞뒤에 둘 수 있다. 수식 AUTONUM은
  선택이며 하나만, 슬롯 **뒤에만** 둘 수 있다. 한글의 수식 AUTONUM은 문단에서
  자기보다 앞에 있는 수식 개체의 번호를 표시하므로, 슬롯 앞의 AUTONUM은
  한 번호씩 밀린다(아래 실측). 서식·위치를 그대로 복제한다. 슬롯은 컨트롤을
  넘을 수 없다. 다른 컨트롤, 쪽 나누기, 목록·개요 번호는 거부한다.
- 슬롯 앞에도 탭을 둘 수 있다. 예를 들어 `<탭>슬롯<탭>(번호)`에 가운데 탭과
  오른쪽 탭을 정의한 스타일을 쓰면 수식은 가운데, 번호는 오른쪽 끝에 놓인다.
- 블록 수식 문단은 표본 문단의 스타일(수식 번호 스타일)을 따른다.
  수식 글자 크기는 문단 스타일과 무관하게 `display_math.fontsize-pt`를 따른다.
- 경계 안에는 표본 문단 하나만 둔다. 코드·그림·표의 앞뒤 빈 문단 복제는 아직
  지원하지 않는다.
- 크기 값은 0보다 크고 소수 둘째 자리까지 받는다. 한글은 이 값을 1/100pt
  단위(HWPUNIT) 정수로 저장한다. 별도 상한은 두지 않았다(아래 실측).
- 크기 설정은 `begin:display_math`보다 앞, 템플릿 정의 영역 안에 둔다.
- init-template은 두 작업기 모두 같은 `슬롯<탭>(번호)` 표본을 만든다. rhwp는 탭
  부가 데이터로 직렬화기의 자리표시 값 `[0,0,0,0,0,0,9]`를 쓰며, 한글이 열 때 탭
  위치를 다시 계산한다(아래 실측). 크기는 한글 작업기가 기본 글자 크기, rhwp가 10pt다.

인라인 수식은 템플릿 선언이 없다. 수식이 들어가는 문단에 적용된 스타일의
글자 크기를 수식 편집기 글자 크기로 넣는다. 문단에 직접 지정한 글자 서식은
반영하지 않는다. 목록 문단과 각주 본문은 각자 자기 스타일의 크기를 따른다.

수식 편집기 글자 크기는 수식 자체의 속성이다. 생성 후에는 사용자가 수식
편집기에서 직접 바꿀 수 있다.

## Hancom 작업기 구현

- 인라인 수식은 각주처럼 `MD2HWP_INLINE_MATH_<guid>` 표식 run으로, 별행 수식은
  표처럼 `MD2HWP_DISPLAY_MATH_<guid>` 표식 본문 문단으로 평면 단계의 기존 검증을
  통과한다. 각주 부착 뒤 `TemplateDisplayMath.Attach`가 표식을 실제 EQUATION으로 바꾼다.
- HWPML 가져오기는 수식 크기·기준선을 다시 계산하지 않는다(아래 실측). 그래서
  서로 다른 (SCRIPT, 크기)마다 작업 문서 끝에서 `EquationCreate`로 수식을 한 번 만들고,
  그 EQUATION의 기하·기본 속성을 복제한다. 작업 문서는 다음 전체 가져오기로 대체된다.
- 생성 수식에는 충돌 없는 새 InstId와 기존 개체보다 큰 새 ZOrder를 준다. 인라인은
  번호 종류 "없음", 별행은 "수식"이다. 수식 AUTONUM 값은 문서 순서로 다시 계산한다.
- HWPML 가져오기는 수식 글꼴을 `HYhwpEQ`로 바꾼다(아래 "수식 글꼴 이름"). 그래서
  마지막 HWP 저장 직전에 생성 수식만 골라 컨트롤 `Properties`의 `EqFontName`을
  `HancomEQN`으로 되돌린다. 컨트롤 순서와 HWPML의 EQUATION 순서(각주 포함)가 같은지
  수식 SCRIPT로 확인하고, 생성 수식은 InstId로 고른다. 템플릿에 원래 있던 수식은
  건드리지 않는다. HWP·HWPX 저장 후 다시 열어 글꼴을 다시 확인한다. 이 단계 뒤의
  저장·재열기 비교가 크기·기준선이 바뀌지 않았는지 확인한다.
- 한 번 만든 수식이 글자처럼 취급되지 않거나 Version이 비어 있으면 실패한다.
  C# dynamic에서 매개변수 집합을 매번 새로 꺼내면 기본값이 적용되지 않아 수식이
  떠 있는 개체로 만들어진 사례가 있었다. 구조 비교는 이 문제를 잡지 못했고 쪽
  이미지에서만 드러났다.
- 저장·재열기 후 기대 XML과의 비교는 수식을 위해 완화하지 않았다.

## rhwp 작업기 구현

- 한글은 파일을 열 때 저장된 수식 크기·기준선을 그대로 쓴다(아래 "HWPML 가져오기와
  수식 기하"와 같은 성질). 그래서 rhwp는 한글 없이 한글과 같은 크기를 계산해야 한다.
  `backends/rhwp/src/equation_metrics.rs`가 그 계산기다. rhwp의 수식 파서로 SCRIPT를
  읽고, 한글 2020으로 잰 글자 폭 표와 구조 규칙으로 폭·높이·기준선을 낸다.
- 측정 근거: `tools/development/measure_hancom_equations.ps1`로 `EquationCreate`
  결과를 잰다. `backends/rhwp/data/`의 `hancom-equation-glyphs.json`(글자 306개,
  4~48px), `hancom-equation-geometry.json`(맞춤용 1390건),
  `hancom-equation-toolbar.json`(맞춤에 쓰지 않은 툴바 수식 152건).
- 한글은 96dpi 픽셀 격자(1px = 75 HWPUNIT)에 조판한다. 줄 높이 h = round(크기/75)px,
  글자 폭은 h와 48dpi 크기 s = 크기/150(.5는 내림)에 따라 달라진다. 첨자는 h를
  0.65배 크기로, s를 부모 s × 0.65의 올림으로 따로 정한다.
- 첨자가 늘리는 높이는 위첨자는 줄 위로만, 아래첨자는 줄 아래로만 늘고, 크기에
  따라 픽셀 반올림으로 불규칙하게 바뀐다. 그래서 고정 비율 대신 3~40pt를 0.25pt
  간격으로 잰 표(`hancom-equation-scripts.json`)를 쓴다. 큰 연산자 위에서도 같은
  양이 연산자 위아래로 붙는다. `int` 높이는 크기를 반 픽셀(37.5)로, `{sum}`은
  41.67 단위로 반올림한 값에 비례한다. 아래 끝만 있는 적분은 끝이 기호 밑으로
  들어가 폭이 거의 늘지 않는다.
- 정확도(오차 절댓값, HWPUNIT): 맞춤 자료 폭 중앙값 0·90%값 40, 높이 90%값 4,
  기준선 90%값 1%p. 툴바 자료 폭 중앙값 11·90%값 75(1px), 높이 90%값 50.
  크기별 높이 자료(`hancom-equation-heights.json`, 459건) 높이 90%값 15~28.
  `cargo test`가 이 기준을 회귀 시험으로 확인한다. 한글과 rhwp 파서가 다르게 읽는
  문법(`root 3 of x`, `sum from … to`, 중괄호 없는 `x^2+1`, `choose`)은 제외한다.
  md2hwp 변환기는 이 문법을 만들지 않는다.
- 표에 없는 글자는 일반적인 폭(한글·한자는 1em)으로 추정한다. 어떤 SCRIPT도
  거부하지 않는다. 문법 검사도 하지 않는다.
- 폭을 작게 추정하면 수식이 뒤 글자를 덮는다. 각주 크기(8pt) 첨자가 3px 좁아
  마침표를 덮은 사례를 쪽 이미지에서 찾아 첨자 크기 반올림을 고쳤다.
- 개체 필드는 한글 작업기가 저장한 HWP를 rhwp로 읽은 값을 따른다. 인라인은 속성
  `0x002A2311`·번호 종류 없음, 별행은 `0x0C2A2311`·번호 종류 수식, 바깥 여백
  좌우 56, 설명문 "수식입니다.", 버전 `Equation Version 60`, 글꼴 이름 `HancomEQN`.
  글꼴 이름은 `EquationCreate` 기본값(`EqFontName`)이다. 아래 "수식 글꼴 이름" 실측 참고.
- 인라인 수식은 각주처럼 `MD2HWP_MATH_<n>_<i>_END` 표식 글자로 조립을 통과한 뒤,
  각주 본문까지 만든 다음 컨트롤로 바꾼다. 크기는 문단 스타일의 글자 크기다.
  별행 수식은 템플릿 표본 문단을 복제해 `slot:display_math` 자리에 넣는다.
- 새 수식에는 충돌 없는 InstId와 기존 개체보다 큰 ZOrder를 준다. 순서는 한글
  작업기와 다르다(별행을 조립하며 먼저 배정). 수식 AUTONUM은 한글 규칙대로
  앞선 "수식" 번호 종류 개체 수로 다시 계산한다.
- 저장·재열기 모델 비교를 수식 때문에 완화하지 않았다.

### rhwp 종단 시험 (2026-11-09)

인라인 수식 4개(본문·강조·목록·각주)와 별행 수식 2개가 든 원고를 같은 템플릿
사본으로 두 작업기에서 만들었다. rhwp 결과는 저장·재열기 비교를 통과했다. 한글
11.0.0.9166에서 열어 HWPML로 내보내니 크기·기준선·번호 종류·글자 크기
(10·14·8pt)가 저장한 값 그대로였고, 수식 AUTONUM은 1·2였다. 110dpi 쪽 이미지에서
두 결과의 배치는 거의 같았다. 수식 폭 차이는 0~2px다(예: 5050 대 4900,
3458 대 3442 HWPUNIT). 한 원고의 시험일 뿐이며 긴 수식·행렬 등 다른 구조의
표시 결과는 확인하지 않았다.

### 대규모 원고 시험 (2026-11-10)

`examples/korean-lorem/large-5x.md` 사본에 인라인 수식 117개(본문·목록·각주)와
별행 수식 32개를 넣어 두 작업기로 만들었다(원본 예제는 바꾸지 않음). 두 결과 모두
작업기 검증을 통과했고, 한글에서 110쪽, 수식 149개(모두 `HancomEQN`), 수식
번호 1~32였다. 생성 시간은 rhwp 6초, Hancom 180초.

- 수식 없는 원본은 두 작업기 결과 106쪽이 72dpi 쪽 이미지에서 모두 같았다.
- 첫 시험에서는 110쪽 중 47쪽만 같았다. rhwp 인라인 수식 높이가 1px 안팎으로
  달라(위첨자 고정 비율, 적분·`{sum}` 높이) 줄 위치가 조금씩 밀렸고, 51쪽 끝의
  그림이 rhwp에서만 다음 쪽으로 넘어갔다.
- 높이 규칙을 실측 표로 바꾼 뒤 51쪽이 같고, 96쪽이 2000픽셀 미만 차이다.
  남은 차이는 별행 수식 폭(최대 4.5px) 때문에 가운데 정렬 수식이 옆으로 몇 픽셀
  움직이는 것이다. 쪽 나눔은 같았다(눈으로 확인한 쪽: 15·26·32·51·52·86).
- 수식 폭을 작게 추정한 곳(`c²` 2px)은 뒤 글자에 붙지만 겹치지는 않았다.
- `\mid`는 변환기가 지원하지 않고, 표 셀에서 참조하는 각주에는 수식을 넣을 수
  없다(IR 규칙). 시험 원고는 이를 피해 만들었다.

## 원고·검증

- Markdown 입력 형식에 `tex_math_dollars`를 추가한다.
  `authoring.rs`의 수식 문법 미지원 진단과 README의 입력 형식 설명을 함께 고친다.
- SCRIPT 길이를 기존 누적 자원 한도에 포함한다. 변환기 자체의 한도(입력 256 KiB,
  토큰 32,768개, 재귀 깊이 96, 출력 4 MiB)는 유지한다.
- 변환 오류는 원고 위치와 변환기의 바이트 위치를 함께 보고한다.

## 버전 영향

IR 0.4는 닫힌 스키마이므로 새 타입을 넣으면 IR 0.6이 된다. 입력 IR과 템플릿
`ir-version`이 정확히 일치해야 하므로 기존 사용자 템플릿은 다시 만들거나
새 선언을 명시적으로 도입해야 한다. 기본 템플릿과 init-template도 수식 선언을
포함하도록 바꾼다. 두 백엔드(rhwp, Hancom) 모두 같은 계약을 구현한다.

## 한글 실측 (2026-11-09)

환경: `DESKTOP-BRTN48S\MOLIT`, 대화형 세션 1, Windows PowerShell 5.1 x64 STA,
한글 11.0.0.9166, `HWPFrame.HwpObject`. 실행 전에 다른 한글 프로세스가 없음을
확인했다. 별도로 띄운 한글 프로세스 하나만 사용했고, 매 실행 후 정상 종료를
확인했다. 원본 `templates/template.hwp`는 사본만 열었고 해시가 바뀌지 않았다.
시험 스크립트와 결과물은 저장소에 넣지 않았다.

### 수식 글자 크기

- `EquationCreate`의 `BaseUnit`과 내보낸 `EQUATION BaseUnit`은 1/100pt 단위
  정수다. 1033(10.33pt)은 저장 후 다시 열어도 그대로다.
- COM은 0, -100, 100000도 오류 없이 받아 그대로 저장한다. 따라서 COM 결과로
  허용 범위를 알 수 없으며, md2hwp가 직접 검증해야 한다.
- 72dpi 쪽 이미지에서 1pt·11pt·127pt·255pt는 크기에 비례해 그려졌다
  (`Hx`의 잉크 높이 1·8·88·177px). 0은 사실상 보이지 않고, 1000pt는 쪽을 넘어 잘린다.
- 수식 편집기 화면의 입력 범위는 UI 조작 없이 확인할 수 없어 확인하지 않았다.
  상한은 별도로 정한다.

### 수식 번호

같은 문단에 수식 개체, 탭, 수식 AUTONUM을 둔 세 문단을 HWPML로 가져오고,
저장 후 다시 연 결과와 쪽 이미지를 확인했다.

| 경우 | 수식 개체 번호 종류 | AUTONUM 위치 | 내보낸 Number | 화면 |
|---|---|---|---|---|
| 기본 | 수식 | 수식 뒤 | 1, 2, 3 | (1) (2) (3) |
| 번호 종류 없음 | 없음 | 수식 뒤 | 0, 0, 0 | (0) (0) (0) |
| 번호를 앞에 | 수식 | 수식 앞 | 0, 1, 2 | (0) (1) (2) |
| 사이에 인라인 | 수식 / 없음 / 수식 | 블록 수식 뒤 | 1, 2 | (1) (2) |

- 수식 번호를 두 번 세지 않는다. 수식 AUTONUM은 별도 카운터가 아니라
  자기보다 앞에 있는 마지막 "수식" 번호 종류 개체의 번호를 표시한다.
- 따라서 블록 수식 개체의 번호 종류는 "수식"이어야 하고, AUTONUM은 슬롯 뒤에
  있어야 한다. `EquationCreate`로 만든 수식의 기본 번호 종류도 "수식"이다.
- 번호 종류 "없음"인 인라인 수식은 블록 수식 번호에 영향을 주지 않는다.
- `InsertAutoNum` action은 이 시험에서 실패했다. 번호는 백엔드가 이미 쓰는
  방식대로 HWPML의 `AUTONUM NumberType="Equation"`으로 넣는다.
- 이 실측은 한글 Hancom 백엔드 결과다. rhwp 백엔드의 번호 계산·표시는 따로 확인해야 한다.

### 기본 템플릿 버전 변경

`templates/template.hwp`의 `{{md2hwp:ir-version:0.4}}`를 사본에서 한글
`AllReplace`로 `0.6`으로 바꾸고 저장·재열기했다. 날짜 요약과 커서 위치를 뺀
HWPML 비교에서 다른 곳은 그림 표본 PNG(BinData 1)의 저장 크기 속성
`Size` 229→226뿐이었다. 디코딩한 PNG 120바이트는 같다. 한글이 다시 저장하며
압축 스트림 크기만 바뀐 것으로 본다.

### HWPML 가져오기와 수식 기하

같은 수식(`{a+b} over {c+d}`, 11pt)을 `EquationCreate`로 만들면 크기 2733×2580,
기준선 65다. 같은 EQUATION을 크기 1×1, 기준선 0으로 바꿔 HWPML로 가져오면
가져온 직후와 저장·재열기 뒤 모두 1×1, 기준선 0 그대로였다. `SIZE`를 빼면
7200×7200이 되었다. 가져오기는 수식을 다시 조판하지 않는다.

### 수식 글꼴 이름

`a + b = c ^{2} + {1} over {x}`(10pt)를 `EquationCreate`로 만들어 HWP로 저장하고
rhwp로 EQEDIT 글꼴 이름을 읽었다.

| 만든 방법 | 저장된 글꼴 이름 | 크기 |
|---|---|---|
| 기본값(`EqFontName` 기본값 `HancomEQN`) | `HancomEQN` | 6415×2250 |
| `EqFontName`=`HYhwpEQ` | `HYhwpEQ` | 6415×2250 |
| Times New Roman, Cambria Math, 없는 글꼴 이름 | 지정한 이름 그대로 | 7315×2475 |
| 만든 뒤 `EquationModify`로 Times New Roman | `Times New Roman` | 7315×2475 |
| 위 수식들을 HWPML로 내보냈다 가져옴 | 모두 `HYhwpEQ` | 원래 크기 유지 |
| 가져온 뒤 컨트롤 `Properties`의 `EqFontName`을 `HancomEQN`으로 | `HancomEQN` | 모두 6415×2250 |

- 한글은 지정한 글꼴 이름을 그대로 저장한다. `HancomEQN`과 `HYhwpEQ`는 같은
  크기로 조판된다. 다른 이름은 없는 글꼴까지 모두 같은 크기여서 하나의 대체
  글꼴로 조판되는 것으로 보인다. 쪽 이미지로는 확인하지 않았다.
- HWPML 내보내기에는 글꼴 속성이 없고, 가져오기는 `Font`·`FontName`·`EqFontName`
  속성을 무시하고 `HYhwpEQ`를 넣는다. 크기는 다시 조판하지 않는다. 그래서
  Hancom 작업기 결과의 수식은 `HYhwpEQ`다.
- 컨트롤 `Properties`로 글꼴을 바꾸면 한글이 다시 조판한다(Times New Roman
  수식이 HancomEQN 크기로 바뀜).
- `GetTextFile`은 `HWPX`·`OWPML` 형식을 지원하지 않는다(빈 결과).
- 같은 이름이라도 저장된 글꼴 이름에 따라 그리는 글자가 다르다. `HYhwpEQ`로 저장된
  수식은 `HancomEQN` 크기 상자 안에 더 굵고 넓게 그려져 `√x`가 뒤 글자에 붙었다.
  `HancomEQN`으로 저장하면 상자 안에 맞게 그려진다(110dpi 쪽 이미지, 두 작업기 모두).
- Hancom 작업기에 글꼴 복원을 넣은 뒤 같은 원고를 HWP·HWPX로 만들었다. 작업기
  검증을 통과했고, HWP의 EQEDIT와 HWPX의 `hp:equation@font` 모두 `HancomEQN`이며
  크기는 이전과 같다.
- GUI 수식 편집기의 글꼴 메뉴는 UI 조작 금지 원칙에 따라 시험하지 않았다.
  같은 편집 동작인 `EquationModify`로 대신 확인했다.

### Hancom 작업기 종단 시험

Release 빌드와 추적 기본 템플릿으로, 본문·강조·목록·각주의 인라인 수식 4개,
별행 수식 2개, 수식 없는 표가 든 원고를 `--worker md2hwp-hancom.exe`로 생성했다.
저장·재열기 비교를 통과했다. 110·300dpi 쪽 이미지에서 인라인 수식은 문장 안에
들어가고, 별행 수식 뒤에 (1)·(2)가 붙으며, 각주 수식은 각주 스타일 크기(8pt)다.
강조 안 수식은 설계대로 굵게 바뀌지 않는다. 표본 문단이 본문 스타일과 탭 하나뿐이라
별행 수식은 왼쪽 정렬이며, 가운데 정렬·오른쪽 번호는 템플릿에서 정한다.
HWPX 출력, Debug의 `--legacy-com` 경로, 긴 수식의 줄바꿈·쪽 넘김은 시험하지 않았다.

### rhwp init-template 표본

rhwp `init-template`으로 만든 템플릿을 Hancom 작업기의 `validate-template`이
통과시켰다. 같은 템플릿과 위 시험 원고를 Hancom 작업기로 생성했을 때 저장·재열기
비교를 통과했고, 200dpi 쪽 이미지에서 별행 수식 뒤 탭 간격과 (1)·(2)가 표시되었다.
