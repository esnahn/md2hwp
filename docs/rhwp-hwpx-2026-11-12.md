# rhwp HWPX 템플릿·출력

구현: 2026-11-12, rhwp 고정 커밋 `e4f8ff2`(upstream devel). 2026-11-23에 `v0.9.1`(`981ce66`) 고정과
표 쪽 넘김 검사용 사본 위로 옮기고 다시 확인했다. IR 0.6, 한글 2020 11.0.0.9136.

`md2hwp-rhwp.exe`는 HWP와 HWPX 템플릿, HWP와 HWPX 출력을 모두 받는다. 한글·.NET·보안 모듈은
필요하지 않다. 문서 조합은 HWPX에서도 HWP 모델에서 하며, HWPX는 파일을 읽고 쓰는 경계에서만
다룬다(`backends/rhwp/src/hwpx.rs`). 이 문서는 그 경계의 처리와 검사, 한글 2020과 다른 변환의 보정,
검증 기록과 확인하지 않은 범위를 적는다. 사용자용 설명은 [HWPX 템플릿과 출력](hwpx.md)에 있다.

## 범위

| 명령 | `.hwp` | `.hwpx` |
| --- | --- | --- |
| 변환(`<ir>`, `ir2hwp`)의 `--template` | 지원 | 지원 |
| 변환의 출력 | 지원 | 지원 |
| `init-template` 출력 | 지원 | 지원 |
| `validate-template` 대상 | 지원 | 지원 |

- 형식은 확장자로 정한다(대소문자 무시). `.hwpx.zip`, `.hml` 같은 다른 확장자는 생성 전에 거부한다.
- 내용도 확장자와 맞아야 한다. `.hwp`는 HWP compound document 시그니처, `.hwpx`는 rhwp의
  `detect_format`이 HWPX 패키지로 판정해야 한다. 이름만 바꾼 파일은 어느 쪽이든 거부한다.
- 기본값은 그대로다. 템플릿은 EXE 옆 `template.hwp`, 출력은 `원고.output.hwp`이다.
- `--worker`를 생략하면 HWP와 HWPX 모두 EXE 옆 `md2hwp-rhwp.exe`를 먼저, 없을 때만
  `md2hwp-hancom.exe`를 고른다. 전에는 템플릿이나 출력이 `.hwpx`이면 한글 백엔드만 골랐다.
  명시한 `--worker`는 그대로 쓰고, 실패한 뒤 다른 백엔드로 다시 시도하지 않는다.
- IR, 템플릿 태그와 선언, 결과 JSON 필드는 바꾸지 않았다.
- 원고 입력은 계속 Markdown과 Pandoc JSON이다. `hwp2pdf.exe`는 계속 HWP 입력만 받고,
  `hwp2pdf.exe`와 `hwpeqrecalc.exe`는 계속 한글을 사용한다.

## 처리 순서

1. 템플릿을 연다. `.hwpx`는 먼저 HWP 바이트로 내리고 원본과 대조한다.
2. HWP 모델에서 조합한다. 떠 있는 표의 쪽 넘김 검사도 여기서 한다.
3. HWP로 저장하고 다시 열어 저장 레코드를 기대 모델과 비교한다. `.hwp` 출력은 여기서 게시한다.
4. `.hwpx` 출력은 그 HWP를 HWPX로 내보내고, 수식 번호 범주를 바로잡고, 다시 열어 HWP와 대조한 뒤
   게시한다.

### HWPX 템플릿 내리기

`hwpx::lower_template`이 HWPX 템플릿을 HWP 바이트로 바꾸고, 그 HWP가 읽은 내용을 그대로 담았는지
확인한 다음에만 기존 HWP 템플릿 경로에 넘긴다. 그 뒤의 처리(원본 AUTONUM 저장값 복원, 정의 읽기,
조합)는 HWP 템플릿과 같다.

1. rhwp로 HWPX를 읽고 HWP 저장용 스냅숏을 만든다(`prepare_hwp_export_snapshot`).
2. HWP로 직렬화한다. 직렬화기가 내용 손실을 보고하면 실패한다.
3. 직렬화한 HWP를 다시 읽어 스냅숏과 upstream 변환 비교(`diff_exported_hwp_documents`,
   `strip_hwpx_to_hwp_noise`)로 대조한다.
4. 구역마다 기본 바탕쪽의 종류(양쪽·짝수·홀수)를 비교한다. 원본 종류를 HWP 저장 순서(양쪽, 짝수,
   홀수)로 정렬한 목록이 스냅숏, 다시 읽은 HWP와 모두 같아야 한다. 어댑터는 종류를 고치지 않는다.
5. 내장 데이터를 (소문자 확장자, 바이트) 목록으로 비교한다. HWPX가 저장 ID를 다시 매기므로 ID는
   비교하지 않는다.

원본 템플릿 파일은 읽기만 한다. 변환이 끝나 게시하기 직전에 템플릿 바이트를 다시 읽어 처음과
같은지 확인하는 기존 검사도 그대로다.

### HWPX 출력

HWPX 출력은 HWP 출력의 검사를 모두 마친 HWP에서만 만든다. 조합한 모델을 HWP로 저장하고, 다시 열어
저장 레코드를 독립적으로 구성한 기대 모델과 비교하는 과정(내장 데이터와 각주 저장값 포함)은
`.hwp` 출력과 같다. 그다음 `hwpx::export`가 다음을 한다.

1. 검증한 HWP 바이트를 다시 열어 HWPX로 내보낸다(`export_hwpx_native_with_report`). 내용 손실
   보고가 있으면 실패한다.
2. 수식의 `numberingType`을 모델 값으로 되돌린다(아래 "한글 2020과 다른 변환").
3. 저장한 패키지를 검사한다.
   - `detect_format`이 HWPX여야 하고, upstream 패키지 검사(`check_package`)를 통과해야 한다.
   - 다시 읽은 문서를 그 HWP와 upstream 내보내기 비교(`diff_exported_hwpx_documents`,
     `hwpx_export_expected_document`, `strip_hwp_to_hwpx_noise`)로 대조한다.
   - 내장 데이터의 (확장자, 바이트) 목록이 같아야 한다.
   - 모든 수식의 (인스턴스 ID, 번호 범주) 목록이 같아야 한다.
   - rhwp가 계산한 쪽 수가 같아야 한다.
4. 패키지를 출력 폴더의 임시 파일에 쓰고 다시 읽어 바이트가 같은지 확인한다.

원고 IR, 템플릿, 그림 원본이 생성 중에 바뀌지 않았는지 확인한 뒤 출력 확장자가 정한 형식 하나만
게시한다. 중간 HWP는 임시 파일로만 쓰고 게시하지 않는다. 어느 단계에서 실패해도 기존 출력은 남는다.
`--verbose`이면 HWP 대조와 HWPX 대조 통과를 따로 보고한다.

### `init-template`와 `validate-template`

- `init-template`은 기존과 같이 HWP 모델을 만들어 저장·재열기·기대 모델 대조·엄격 검사를 통과시킨다.
  출력이 `.hwpx`이면 그 HWP를 위 HWPX 출력 과정으로 내보내고, 저장한 HWPX를 다시 템플릿 내리기로
  HWP로 바꿔 엄격 검사를 한 번 더 통과해야 게시한다. 기존 경로는 게시 시점에도 덮어쓰지 않는다.
- `validate-template`은 `.hwpx`를 템플릿 내리기로 HWP로 바꾼 뒤 기존 엄격 검사를 한다. 검사 전후의
  원본 바이트가 같은지도 확인한다.

## 한글 2020과 다른 변환

### 수식 번호 범주

rhwp의 HWPX 저장기는 수식마다 `numberingType="EQUATION"`을 적는다(`e4f8ff2`와 `v0.9.1` 모두
`src/serializer/hwpx/section.rs`의 `hp:equation` 서식 문자열). 모델에는 수식마다 번호 범주가 있고,
md2hwp가 만드는 본문 속 수식은 한글 2020이 저장한 대로 범주가 없음(`NONE`)이다. 그대로 두면 한글이
본문 속 수식에도 수식 번호를 매겨 별행 수식 번호가 밀린다.

어댑터는 저장한 패키지의 `Contents/*.xml`에서 `hp:equation` 요소를 인스턴스 ID로 찾아 범주가
`EQUATION`이 아닌 수식의 이 속성 하나만 모델 값으로 고쳐 쓴다. 다른 바이트와 압축 방식은 그대로
복사한다. 고쳐 쓴 수가 대상 수식 수와 다르거나, 같은 인스턴스 ID에 범주가 다른 수식이 있으면
실패한다. 다시 읽은 HWPX의 범주 목록도 HWP와 대조한다.

upstream이 저장된 범주를 그대로 적게 되면 고칠 속성이 없어 이 검사가 실패한다. 그러므로 고정 커밋을
옮길 때마다 수식 원고의 HWPX 출력을 확인하고, upstream이 한글과 같아지면 이 보정을 지운다.

### 바탕쪽 순서

HWPX 템플릿을 HWP로 내리면 바탕쪽은 종류와 내용을 유지하고 저장 순서만 HWP 순서(양쪽, 짝수,
홀수)로 바뀐다. 종류가 바뀌던 문제는 upstream 이슈 #9046으로 `e4f8ff2`에서 고쳐졌고 `v0.9.1`에
포함됐다. 한글 2020으로 만든 바탕쪽 조합 11건을 rhwp로 내린 결과는 한글이 같은 HWPX를 HWP로
저장한 것과 종류·내용이 모두 같았다. 어댑터는 종류를 고치지 않으며, 내린 모델이나 다시 읽은
HWP의 종류가 원본과 다르면 실패한다.

### 변환행렬 계수

변환행렬 계수는 HWPX를 거치며 단정밀도로 저장된다. 한글 2020의 HWPX 저장도 같다. 보정하지 않으며,
아래 예제에서 표시 차이는 없었다. 한글 백엔드의 최종 HWPX 검증이 하는 비교용 정규화와는 별개다.

## 검증 기록 — 2026-11-12 (`e4f8ff2`)

한글 2020 11.0.0.9136에서 150 DPI 쪽 이미지로 비교했다.

- 예제 13종과 수식 원고 1종을 추적 템플릿(HWP)과, 그 템플릿을 한글이 HWPX로 저장한 템플릿으로
  각각 HWP·HWPX로 출력해 56개 파일을 만들었다. 모두 한글에서 열렸다.
- HWP 템플릿→HWP 출력을 기준으로 나머지 세 조합 42건 501쪽이 모두 픽셀 단위로 같았다.
- rhwp `init-template`의 HWP·HWPX 템플릿(각 2쪽)과 그 템플릿으로 만든 전체 기능 원고(각 6쪽)도
  같았다.

## `v0.9.1` 위 재확인 — 2026-11-23

HWPX 커밋을 `v0.9.1` 고정과 표 쪽 넘김 검사용 사본(`perf/rhwp-table-breaks`) 위로 옮겼다. 그 아래의
devel 고정 커밋 여섯 개는 기반 브랜치에 같은 변경이 있어 빠졌다. 충돌은 `backends/rhwp/src/main.rs`
(쪽 넘김 검사가 조합 안으로 옮겨 간 자리)와 `docs/rhwp-backend-strategy.md`뿐이었다. 어댑터의 HWPX
코드는 바꾸지 않았다.

- upstream의 HWPX 읽기·쓰기 코드(`src/parser/hwpx`, `src/serializer/hwpx`)에서 `e4f8ff2`와 `981ce66`이
  다른 곳은 `header.rs` 하나다. 패키지 `xmlVersion` 1.4 이상에서 `hp:switch` 밖에 평문으로 적은
  고정·최소·여백 줄 간격을 두 배로 읽고 반으로 쓴다. 한글 2020이 저장한 HWPX(바탕쪽 사례 11건,
  `xmlVersion="1.4"`)와 아래 비교에서 rhwp가 내보낸 HWPX 19개는 줄 간격을 모두 `hp:switch` 안에
  적으므로 이 경로에 닿지 않는다.
- 수식 `numberingType="EQUATION"` 서식 문자열은 `v0.9.1`에도 그대로라 보정을 유지한다. 아래 비교의
  `all-features` HWPX 출력 3건에서 별행 수식 3개는 `EQUATION`, 본문 속 수식 8개는 `NONE`으로 저장됐다.
- `cargo test --workspace`(662개 통과, 수동 수식 측정 4개 무시), `cargo clippy --workspace
  --all-targets -- -D warnings`, Release `build.ps1`(제3자 고지 검사 포함)을 통과했다.

옮기기 전 작업기(`68f2cf0`, `e4f8ff2`)와 옮긴 작업기의 Release 결과를 바이트로 비교했다. 원고는 예제
6종(`all-features`, `object-sources`, `footnotes`, `metadata`, `layout-issues`, `large-5x`), 템플릿은
추적 `templates/template.hwp`와 옮긴 작업기의 `init-template`으로 만든 HWP·HWPX 템플릿이다. 두 작업기에
같은 템플릿 파일을 주고 HWP·HWPX로 출력해 36쌍을 만들었다.

- 32쌍이 바이트까지 같다. 추적 템플릿의 HWPX 출력 6건과 `large-5x`의 여섯 조합이 모두 여기에 든다.
- 다른 4쌍은 `all-features`를 `init-template` 템플릿(HWP·HWPX)으로 만든 HWP·HWPX 출력이다. HWPX의
  `Contents/section0.xml`은 옮기기 전 결과에 있던 쪽 나눔 하나(`pageBreak="1"`)만 없고 나머지와
  `header.xml`이 같다. 이 쪽 나눔은 기반 브랜치의 `e665268`(검사용 사본에서 글자처럼 취급하는 그림의
  캡션 높이를 셈)이 없앤 것이며, 그 HWP 결과는 한글에서 8쪽으로 확인했다
  ([글자처럼 취급하는 그림의 캡션](rhwp-backend-strategy.md#글자처럼-취급하는-그림의-캡션--2026-11-19)).
- `init-template` 결과(HWP·HWPX)도 다르다. HWPX에서는 `Contents/section0.xml`의 원고 표 원형에
  `flowWithText="1"`이 생긴 것뿐이다. 기반 브랜치에 있던 `9f894e8`(떠 있는 표를 쪽 영역 안으로
  제한)이 옮기기 전 브랜치에는 없었기 때문이다. 같은 작업기로 두 번 만든 템플릿은 서로 같다.
- 세 템플릿 모두 `validate-template`을 통과했다. Release 작업기 1회: `large-5x` HWP 출력 4.3–5.5초,
  HWPX 출력 6.5–6.9초.

바이트가 같은 결과는 한글에서 다시 열어 보지 않았다. 다른 결과 가운데 `all-features`를 `init-template`
HWP 템플릿으로 만든 HWP·HWPX는 한글 2020(11.0.0.9166)에서 열어 100 DPI 쪽 이미지를 비교했다. 둘 다
8쪽이고 8쪽 모두 픽셀까지 같다. `init-template` HWPX 템플릿으로 만든 `all-features` 출력과 `init-template`
HWPX 템플릿 자체는 한글에서 열어 보지 않았다. 한글이 HWPX로 저장한 추적 템플릿과 수식 원고는
이번 비교에 넣지 않았다(그 템플릿 파일을 남겨 두지 않았다).

## 확인하지 않은 것

- 한글이나 rhwp가 저장하지 않은 HWPX 템플릿. 다른 프로그램이 저장한 패키지는 내리기 대조를
  통과해도 검증 범위 밖이다.
- 한글 백엔드 `init-template`으로 만든 HWPX 템플릿을 rhwp로 쓰는 경우. 그 템플릿은 한글 백엔드의
  변환에서 거부되는 사례가 있다([재현과 구분](backend-selection-2026-10-23.md)).
- 한글 외 뷰어의 HWPX 표시, 같은 원고의 한글 백엔드 HWPX 결과와의 비교.
- 구조 검사와 쪽 수 비교는 한글의 줄바꿈·쪽 배치·잘림을 보장하지 않는다. 긴 표·글상자의 기존
  배치 한계는 HWP 출력과 같다([rhwp 백엔드 범위](rhwp-backend-strategy.md)).

```powershell
pwsh -NoProfile -File tools/development/build.ps1 -Configuration Release
.\target\release\md2hwp-rhwp.exe init-template --output 새템플릿.hwpx

.\target\release\md2hwp-rhwp.exe examples\all-features\all-features.ir.json --output 결과.hwpx --template 새템플릿.hwpx --verbose
```
